# Changelog

All notable changes to this project are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project aims to follow [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Breaking

- **Lazy home folder (`@secret-desk/core`, `@secret-desk/automation`):** the constants `DEFAULT_VAULT_FILE` and `DEFAULT_PROFILE_DIR` are removed; they called `os.homedir()` when the module was imported. Use the functions `defaultVaultFile()` and `defaultProfileDir()` instead, which look the home folder up when called. A constant string cannot be computed lazily, so no deprecated alias is kept. `agentTokenPath(home)` of the desk app now requires the home folder, and `loadOrCreateAgentToken(path, ...)` requires the path (both are internal to the app).

### Added

- **Route functions on the portable runtime entry (`@secret-desk/runtime/portable`):** the functions behind the inventory, issuance, approval, variable and evidence routes (`listSecrets`, `getSecret`, `overview`, `addSecret`, `updateSecretMeta`, `requestIssuance`, `confirmIssuance`, `rejectIssuance`, `listIssuances`, `listApprovals`, `resolveApproval`, `listVariables`, `addVariable`, `requestApplyVariable`, `listEvidence`, `evidenceSvg`, `authorize`, `authorizeSystem` and the others listed in `portable.ts`, with their types and errors) are exported by name and take a `RuntimeCore`, so an embedder that built a runtime with `createPortableRuntime` serves those routes with the same functions the desk app, the CLI and the MCP server use: same authorisation hook calls, same revoke gate, same results. Nothing in the root entry or the local edition changes. `agent-api.ts` was split into `agent-api-core.ts` (no Node API) and `agent-api.ts`, which re-exports everything of the core module under the same names; the environment file export `exportEnv` stays there. `evidenceSvg` of the portable entry takes an optional translate function (the local one binds the English catalogue and keeps its signature and output). Small extractions, each re-exported by the old module as the same object: `known-connections.ts`, `facade-registry.ts`, `neededRights` and `teamPermissions` in `team-token-rights.ts`. The root entry gains one name, `agentMayWriteEnvFile` (a file-name check for the environment file target; it replaces a `node:path` call by a string helper tested against `path.posix.basename`). No export was removed or renamed.
- **Portable runtime entry `@secret-desk/runtime/portable` (`@secret-desk/runtime`):** a subpath whose value-import closure contains no `node:` specifier, no libsodium, no browser automation and no file access, and which takes the core and the providers only from their portable entries. `createPortableRuntime(source, options)` builds the runtime from parts the embedder opens itself (`{ config, inventory, evidence, configPath? }`, for example `parseConfig`, an `InventoryStoreCore` on a memory backend and the memory evidence store) and returns a `RuntimeCore`. Extra options: `providers` (a registry or a function that makes one; default `createPortableRegistry()`) and `automation` (a function that makes the `AutomationPort` from the providers the builder created; default `noAutomation`, which offers no browser and refuses to run anything with an `AutomationUnavailableError`; `noAutomationFor(now)` is the same port on a given clock, which the builder uses when a clock was injected). Only the options of `PortableRuntimeOptions` are read: any other key, from an untyped caller too, is ignored. The pieces only the Node entry needs (the defaults for sealing and signing, the class of the GitHub client, the factory of the connection store) are a separate argument of an internal builder that is not exported from the portable entry or the package root. A runtime that cannot seal or sign (no injected `seal`/`sign`, no host) refuses with a `HostCapabilityError` before any request; the build fails early with a clear error when `globalThis.crypto.randomUUID` is missing. The entry also exports `InstanceState`, `IssuanceQueue`, `PendingStore`, `ApprovalQueue`, the GitHub crypto helpers, the host interface with `HostCapabilityError`, and the automation port types. `createRuntime`, `createLocalRuntime` and the local edition behave as before; `runtime.ts` is now the Node module on top of the portable builder (`runtime-core.ts`). New internal modules: `host-core.ts`, `automation-port.ts`, `github-crypto-core.ts`, `live-check-notify.ts`; `host.ts`, `automation.ts`, `github-crypto.ts` and `live-check-store.ts` keep their exports (same classes and functions). `ARCHITECTURE.md` has a section on the entry. Type-level changes visible to embedders (none breaks a call that compiled before): `RuntimeHost.openVault` returns the portable base class `Vault` (a `SecretVault` still fits), `Runtime` now extends `RuntimeCore`, `issuanceDeps` takes a `RuntimeCore`, `ApprovalQueue.revalidate` takes an `InventoryStoreCore`, and `AutomationPort`, `AutomationManager.browserHostOf` and the automation shape types are new exports of the root. At run time nothing changes for the local edition: `Runtime.connections`, `Runtime.github`, `Runtime.inventory` and the other fields are instances of the classes they were before (`node-runtime-classes.test.ts`). `RuntimeHost` has one new optional member keyed by the symbol `HOME_PATHS` (`{ style, join }`, type `HostPaths`), which `nodeRuntimeHost()` fills from the platform of the process (a symbol key, so the named members of the Node host are unchanged; `nodeHomePaths(platform)` builds it); `expandHomeFor` uses them so that it returns or throws exactly what it did before on both path styles (`host-core.test.ts` compares it with a copy of the old implementation). A host that brings none gets POSIX rules for `~` and `~/x`, as the old code did on a POSIX machine; one deliberate difference: a `~\x` path is now refused with a `HostCapabilityError` (capability `pathStyle`) when the host does not say whether it is POSIX or Windows (the old code returned it unchanged on POSIX), and a `join` of the host that throws or returns no text is refused the same way. The key is a registry symbol on purpose (two loaded copies of the package still find it); the host is trusted by definition.
- **`RuntimeOptions.seal` and `RuntimeOptions.sign` (`@secret-desk/runtime`):** the injectable GitHub client options (`SecretSealer`, `AppJwtSigner`) can be passed to `createRuntime`, so an embedder without Node built-ins can write GitHub secrets and sign GitHub App tokens. A runtime with a host behaves as before. Without a host and without the option, sealing and App signing are refused with a `HostCapabilityError` (capability `seal` or `sign`) instead of reaching libsodium or `node:crypto`. Writing a secret (`putSecret`) and the write probe check the seal capability first, so a runtime that cannot seal makes no request for them. The signer must sign for the App named by `github.auth.appId`. One shared answer, `githubAppUsable(rt)` / `githubAppKeyStatus(rt)` (an injected signer or a connected stored key), now drives team sync, `listConnections`, the connection check of `github-app-key` and the CLI doctor: with `sign` and no stored key the connection is listed as connected with the new source `injected` (the key is held by the embedder); a stored key is shown as before and wins when both exist.
- **Host guard for the library packages:** `host-guard.test.ts` also scans `packages/core`, `packages/automation` and `packages/providers`, with a narrow per-file allow-list that names the findings and the reason.

- **Instance state, deadline on every access and a sweep hook (`@secret-desk/runtime`):** a runtime now keeps everything it holds while it waits for a person in the instance (`Runtime.instance`, an `InstanceState`) and no longer in module scope, so two runtimes in one process share nothing: the one-time code, authorization and identity-verification questions of the provider sign-in flows, the questions of the team token run and the live-check flag used to be module-level and keyed by provider id only. Every question has a deadline of its own, counted from the moment it is asked (`WAIT_WINDOWS_MS`, none longer than 15 minutes), carries the run that asked, and cannot be answered past it or by another run (`WaiterBook`, `WaitExpiredError`, mapped to the time-out failure code). A review that an operation has claimed is held only until its deadline plus two minutes (`CLAIM_GRACE_MS`); then the queue takes it back and aborts the claim's signal (`commitIssuance` takes `options.signal` and `options.hardBound` and checks both, the clock included, before each write; a write already in flight is not cut off, and a write that never settles keeps the commit's own reference to the value). A commit that started a write and did not finish is `partial` (`issuanceStateOf`): the evidence report names the places the new value is at or may be at, and nobody revokes it but a person; an evidence failure after every place was written is a warning in the result, and the item counts as committed. New `RuntimeOptions.now` (the clock for every deadline, also `Runtime.now`) and `Runtime.sweep(now?)`, which removes everything expired and returns the earliest deadline that remains (or `null`) for an embedder to call from a timer or an alarm; it is not behind the authorisation hook on purpose. The local edition keeps its one-minute timer and only calls `rt.sweep()`. Tests: `instance-isolation.test.ts` (two runtimes, a wait started in one and the answer delivered to the other, both ways), `instance-state.test.ts`, `state-guard.test.ts` (fails on module-level mutable state under `packages/runtime/src` and `packages/core/src`; three object-keyed `WeakSet`s and two read-only byte fixtures are listed exceptions; `DEFAULT_NAMING` is frozen and a few constants got `Readonly` types). The runtime's deadlines, including the team token run's time-out, use one clock (`RuntimeOptions.now`); time-outs inside the browser automation package use the system clock. Strings cannot be erased in this runtime: an expired value is unreachable through the queue, not overwritten.
- **Pluggable store for pending reviews (`@secret-desk/runtime`):** `RuntimeOptions.pendingStore` takes a `PendingStore` (`put`, `get`, `list`, `delete`); the default is `MemoryPendingStore`. The store is handed a `PendingRecord` only (identifier, secret id, the entry's provider, created-at, expires-at and the provider's identifier of the new value): the value stays in a map private to the queue, so a store cannot persist it and no longer has to return the same object. The rule: revoking a value that is in use is worse than leaving an unconfirmed one valid, so in doubt nothing is revoked. `Runtime.sweep` revokes only the unconfirmed value of a review this process itself held, never while a commit is working on it or after it wrote a place, and never a record it holds no review for (`IssuanceQueue.orphans()` lists them). Revoking such a record is an explicit call, `IssuanceQueue.revokeOrphan(id, deps, { acceptPartial? })`, which refuses (and drops a stale record) when the entry now holds that identifier, is gone, or has another provider, and returns the gate's typed result (see the next entry). A delete that fails is not reported as settled; it is retried after a growing wait, at most `MAX_REVOKE_TRIES` times, then `RuntimeOptions.onRevokeAbandoned` is told and an evidence note is written (the record stays). Confirm and reject answer an unknown id with "gone" without asking the authorisation hook (ids are random; an authenticated person can tell "gone" from "not allowed"), and the clean-up sweep inside confirm runs only after the person was authorised. A review the queue no longer has is reported as `IssuanceGoneError` (a `PolicyError` with `code: "issuance-gone"`); the portal answers it with 404 (it was 403 before) and its review page offers to generate the value again.
- **One gate for revoking a newly issued value (`@secret-desk/core`, `@secret-desk/runtime`):** `revokeNewValue` is the only code that asks a provider to revoke the new value of a review; commit's stale checks, `discardIssuance`, the sweep and its retries, a person's reject and `IssuanceQueue.revokeOrphan` all go through it (`revoke-gate-guard.test.ts` guards that; the old-value revoke after a confirmed commit and the undo in `prepareIssuance` stay outside; the environment export and the rotate flow go through the gate too, see the first entry under Fixed). It refuses without calling the provider, with a typed reason: `write-started` (a write of the item to any place was ever started, set before the first write is sent, recorded in the store through `commitIssuance`'s new `beforeWrite` hook (a failing store update means no write), never cleared, a failed or timed-out write included; only a person's reject with `acknowledgeWritten` or `revokeOrphan(..., { acceptPartial: true })` lifts it), `value-in-use` (the identifier is the current external id of the secret or of a companion entry, read at that moment), `secret-gone`, `provider-changed`, `no-id`, `no-revoke`. A `write-started` refusal keeps the record, marks it `needsDecision`, writes an evidence note and tells the new `RuntimeOptions.onNeedsDecision`; the other refusals drop a stale record. Consequences: re-confirming a partial item whose entry went stale revokes nothing; a single-place write that timed out is never revoked by the sweep after expiry; a second review of the same provider identifier does not revoke the confirmed one; a record left by a process that died mid-commit is refused without acknowledgement; `rejectIssuance` refuses an item a write was started for with `IssuanceWrittenError` (code `write-started`, the places; the portal answers 409 with `places` and takes `acknowledgeWritten` from the body; the review page shows the message, no new control), removes the queue entry only after the discard settled and owes a failed delete in a `finally`; a failed delete on the stale path is owed too; a discard's delete result is kept apart from saving its report; a commit whose provider returned no identifier clears the entry's external id. `revokeOrphan` also refuses (`not-expired`) a record whose deadline plus the claim grace has not passed unless it is flagged `needsDecision` (on a shared store it may be another runtime's live review); an acknowledged revoke that worked adds an evidence check `revoked-written` naming the places (an acknowledged reject that failed keeps its acknowledgement for the retries); a value the provider issued without an identifier gets a report line saying that it could not be deleted because the provider named none. What remains: a value whose write was started is never revoked automatically, so an unconfirmed value can stay valid at the provider until a person decides or the provider expires it; the gate knows only the inventory, not uses outside it. Known limitations: the guard test is a text check of source files with blind spots, not a proof; the portal has no control to send the acknowledgement and does not list reviews kept for a decision (the API and `onNeedsDecision` exist, the product surface is follow-up work); two reviews of one secret can be confirmed concurrently (as before).

- **Host capability for the runtime (`@secret-desk/runtime`):** new option `RuntimeOptions.host` (type `RuntimeHost`, extends `ConnectionHost` with `runCommand(command, cwd)`, `gitOrigin(dir)`, `gitCheckIgnored(path)`, `homeDir()`, `openVault(options)`, `launchLocalBrowser(options)`, `connectRemoteBrowser(options)` and `findChrome(preferred)`). `createRuntime` forwards it to the connection store and to every path that used to reach the machine on its own: the team token from `SECRET_DESK_TEAM_TOKEN`, the team start-up settings (`SECRET_DESK_TEAM_REPO`, `_PATH`, `_BRANCH`, `startupTeamSync`, `teamSyncFromEnv`), the remote browser and viewer addresses, the default vault, the local browser (driver and Chrome lookup), a remote browser at a configured endpoint, the home folder (`~` paths, default links file and browser profile, the allowed link root), template commands and the Git ignore check of `exportEnv`, and the Git remote checks of `setLink`, `scanLocal` and `listRepos`. Without a host (option omitted or `null`) none of these paths reads the process environment or the home folder or starts a process, and there is no fallback to the Node host: a source is reported as not available, there is no default vault, a browser is refused with `BrowserNotAvailableError` (also a configured remote endpoint, which is not even probed), a `~` path or a default location needs an explicit path (`HostCapabilityError`), the entries of a template command stay empty with a warning, `gitIgnored` is `null`, no remote is known. Template commands also run only in a folder under `policy.envRoots` or the linked folder (checked by real path before anything starts), and the repository's own `node_modules/.bin` binary is used only when it really lies inside that folder. That binary is code controlled by the repository: a `node_modules/.bin/supabase` inside an allowed root or linked folder runs when a person with `runCommands` asks for the template command there. Empty and relative `policy.envRoots` entries are ignored now (for links and for template commands); they used to be read against the current folder of the process. `git` gets an environment built from the host's environment source, with the system and the user's global Git configuration switched off, `-c core.fsmonitor=false -c core.untrackedCache=false` (a repository's own config can otherwise make `git check-ignore` run a program) and `--` before the path or name. `openVault` names the vault file from the host's home folder when the configuration names none, and a `homeDir` that throws counts as no home folder. The path checks are check-then-use and assume the allowed roots are not writable by an attacker. The public option `automationDriver` replaces the browser and is available without a host; the status probe of a configured remote address still runs with it. Importing the runtime does not use the home folder through its own code, but `DEFAULT_VAULT_FILE` (core) and `DEFAULT_PROFILE_DIR` (automation) are public constants computed with `os.homedir()` once at import. The portal's demo mode starts with `vault: null` and never opens the real vault. Exceptions: the YAML parser reads its own debug switches `LOG_TOKENS` and `LOG_STREAM`; file access through configured paths and the Node-only modules of `@secret-desk/core` are not behind the capability. New `nodeRuntimeHost({ env, exec })` is the host of the local edition and `createLocalRuntime(path, options)` is `createRuntime` with it; the portal and the CLI use it, so their behaviour does not change. `writeEnvFile` accepts `checkIgnored`, `gitCheckIgnored` is exported, and `runEnvCommand` refuses a command name that is not on its allow-list. New behavioural test `host-capability.test.ts` builds a hostless runtime from a configuration with the defaults, with the environment replaced by a recording proxy and the child-process starters mocked to throw, and exercises a token read, an environment-file build with commands, a repository link, a recipe run and `info()`. New guard test `host-guard.test.ts` fails when a runtime source file other than `host.ts` reads the process environment, imports `node:os`, `node:module` or `node:child_process`, or uses `new SecretVault`, `defaultKeySource`, `PlaywrightDriver` or `findChrome`; the portable-module guard of the core also rejects `process[...]` and `globalThis["process"]`. See [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md), section "Host capability of the runtime".
- **Importable store contract suites (`@secret-desk/core/testing`):** the contract tests for the inventory backend, the evidence store and (new) the vault store moved into `packages/core/src/testing/` and are exported as `inventoryBackendContract`, `evidenceStoreContract` and `vaultStoreContract`, so an implementation outside this repository (for example on a SQL database in a runtime without Node built-ins) runs the same cases instead of restating them. The suites take the test framework as an argument (`{ describe, it, expect }`), so there is no dependency or peer dependency on a test runner; factories may be async and return an optional `cleanup`, and an optional `run` wraps every test body for stores that only work inside a special context. The modules are portable (no Node built-ins, no `Buffer`, no file system) and guarded by `portable-modules.test.ts` as their own root. The subpath is not re-exported from the package root or from `./portable`. The existing contract tests now run the exported suites against the memory and file implementations; the vault store contract is new (empty read, round trip, replace, binary safety, copies, isolation, `Vault` on top). No change in behaviour of the package. See [ARCHITECTURE.md](docs/ARCHITECTURE.md#running-the-store-contracts-on-another-implementation).
- **Portable GitHub client (`@secret-desk/core/portable`):** the client moved into `github-core.ts` (no Node built-ins, no `Buffer`, no libsodium, no zod) and `GitHubClient` and `githubAppProvider` are exported from the portable entry. The portable client has no default sealer and no default App JWT signer: the caller passes `seal` and `sign`; without them it fails with a clear `GitHubError` instead of loading a default. Base64, Base64URL and UTF-8 conversions use portable helpers (`base64.ts`), and `placeKey` and the snapshot types moved to `place-key.ts` (re-exported by `status.ts`) so the client no longer pulls the zod schemas. `github.ts` stays the Node facade with the same names and behaviour (libsodium default sealer, `privateKey` signing with `node:crypto`), so no import changes. The portable-modules guard now covers the client. See [ARCHITECTURE.md](docs/ARCHITECTURE.md#injectable-cryptography).
- **Authorisation hook for unattended work (`@secret-desk/runtime`, `apps/desk`):** the hook is now also asked before the runtime acts on its own, with a new actor kind `system` (`SystemActor`, `{ kind: "system", name }`, `name` from the closed list `SYSTEM_ROUTINES`: `team-sync-startup`, `sign-in-scheduler`, `live-check-scheduler`). `AuthorizationRequest.actor` is now `Actor | SystemActor`; `Actor` and `ActorRef` are unchanged (`human` or `agent`), so a system actor can neither pass a policy function nor be recorded on a review or an approval, and no portal or agent API input can produce one (new tests on both route prefixes; the actor path `authorize` also refuses any other kind with the new fault reason `invalid-actor` without asking the hook). The expiry sweep of unconfirmed reviews is deliberately not asked and unchanged: it is clean-up that only discards a value and revokes it at the provider, and no hook may extend the lifetime of a value. The start-up team sync asks `team.sync.configure` and `team.sync.apply` (subject `mode: merge`); each scheduled sign-in check and the scheduled live check ask `automation.run` (subject `connectionId`: the recipe id for a sign-in check, none for the live check). `LiveCheckTick.skipped` can now be `"refused"`; the scheduled live check logs one line when it turns from allowed to refused, not one per tick. The failure rules are those of the existing hook (same function): a refusal skips that unit of work, is reported to `onAuthorizeFault` (new optional field `routine` with the fixed routine name, set only when the fault came from a routine) and logged without a value, and never stops a timer; with no hook nothing changes. What a refusal leaves behind: a refused start-up `team.sync.configure` writes nothing and the next start asks again; a refused start-up `team.sync.apply` leaves the configuration written (the allowed first step), the inventory empty and the team state unchanged, and is not retried automatically, a person applies the sync in the portal (which asks the hook as that person); a refused sign-in check records no answer but remembers the attempt time, so the host is asked again only after the retry time. **For people who embed the runtime with a hook:** the hook now also receives `actor.kind === "system"`; a hook that branches on the kind must treat an unknown kind as a refusal. Read-only unattended paths and the command line stay unhooked, see [ARCHITECTURE.md](docs/ARCHITECTURE.md#authorisation-hook).
- **Authorisation hook and who-did-what records (`@secret-desk/runtime`, `@secret-desk/core`):** `RuntimeOptions.authorize` (an `Authorize` function) is called before sensitive actions (issuance prepare, confirm, reject and manual value, approval resolve, inventory edits, variable apply, connection token store and remove, evidence attach, browser run, GitHub sync), after the built-in checks and before the first side effect, so it can only refuse more, never allow what the built-in rules refuse. A refusal is a `PolicyError`; any other failure of the hook (a throw, a return value other than `undefined`, no function, no answer within `RuntimeOptions.authorizeTimeoutMs`, default 10 s) becomes one generic refusal, optionally reported by class name to `RuntimeOptions.onAuthorizeFault`. The hook is also asked for team sync, team import, stage and repository-link changes, the deep connection check, the guided sign-in and team token steps, browser runs, every env export (`exportEnvContent` is now async) and for what an approval causes after it is approved. Confirming and rejecting a review claim it before the hook is awaited, so a slow hook cannot lead to a commit after a discard or to two discards; core refuses to discard or commit an item twice. `Actor` gains an optional opaque `principalId` that nothing sets by default. A pending review records `preparedBy`, `requestedBy` and `approvalId`, an approval records `requestedByRef`, `decidedBy` and `decidedAt`, and the confirmation in the report carries the `principalId` when there is one; the API responses and both OpenAPI descriptions list the new fields (names and ids, never values). No roles, sign-in or rules are added: with no hook configured, behaviour is unchanged. See [ARCHITECTURE.md](docs/ARCHITECTURE.md#authorisation-hook).
- **Injectable cryptography in the GitHub client (`@secret-desk/core`):** `GitHubClientOptions.seal` (a `SecretSealer`) replaces the libsodium sealed box, and `GitHubAppOptions.sign` (an `AppJwtSigner`) replaces signing the App JWT with an in-process private key; `privateKey` is now optional, exactly one of the two must be given. libsodium moved to `github-seal-libsodium.ts` and is loaded lazily, only when no sealer is injected. The local edition behaves as before, with identical output bytes and no new dependency. libsodium is now loaded at the first seal, so a missing or broken libsodium surfaces at the first write or write probe instead of at start-up. New `GitHubClient.seal()` checks the sealer's result (non-empty Base64, not the plaintext, not its Base64) before anything is sent, and the connection write probe now seals through the client's sealer. See [ARCHITECTURE.md](docs/ARCHITECTURE.md#injectable-cryptography).
- **Portable entry point `@secret-desk/core/portable`:** re-exports only the modules without Node built-ins and without libsodium (secret value, stages, inventory types, inventory store core and backends, evidence, vault core, connection store core, variable sources), so a runtime without Node APIs can import the core without bundling `node:fs`, `node:child_process` or libsodium. The package root is unchanged; `@secret-desk/core` now declares `"sideEffects": false` (no module runs code with an effect at import time), so a bundler can drop its unused Node modules. The portable-modules guard now takes the entry point as a root and rejects every npm import except `yaml` and `zod`. No change in behaviour. See [ARCHITECTURE.md](docs/ARCHITECTURE.md#portable-entry-point).
- **Portable inventory store in `@secret-desk/core`:** the logic of `InventoryStore` moved into `InventoryStoreCore` (`inventory-store.ts`, no Node built-ins, covered by the portable-modules guard); `inventory.ts` is now a thin Node facade that adds `open(path)` and the file backend, and re-exports everything, so no import changes. New `MemoryInventoryBackend` (one document, counter revision, one writer at a time, `replaceExternally` to simulate another writer) and a contract suite that runs the same cases against the file and the memory backend. No change in behaviour, stored bytes or messages. See [ARCHITECTURE.md](docs/ARCHITECTURE.md#storage-seams-in-core).
- **Host capability for connection tokens in `@secret-desk/core`:** the token lookup moved into the portable `ConnectionStoreCore` (`connections-core.ts`). Reading an environment variable and running `op read` now sit behind an explicit `ConnectionHost`; `ConnectionStore` supplies the local one (`nodeConnectionHost`) by default and keeps its options, so the local edition behaves as before. A store without a host (`ConnectionStoreCore`, or `ConnectionStore` with `host: null`) reports `env` and `op` sources as not available instead of reading the process. See [ARCHITECTURE.md](docs/ARCHITECTURE.md#host-capabilities).
- **Inventory storage seam in `@secret-desk/core`:** all file access of `InventoryStore` (stat stamp, read and hash, lock file, atomic write, directory watch) moved behind the new `InventoryBackend` interface (`inventory-backend.ts`, no Node built-ins) with `FileInventoryBackend` as the file implementation. Revisions are opaque strings, so the store no longer hashes itself. New `InventoryStore.withBackend(backend, initial?)` for other backends; `open`, `fromText`, `save`, `watch` and the mutators are unchanged, and so are the stored bytes and all messages. The error classes moved to `inventory-errors.ts` and are still exported from `inventory.ts`. See [ARCHITECTURE.md](docs/ARCHITECTURE.md#storage-seams-in-core).
- **Storage seams in `@secret-desk/core`:** the vault encryption moved into `vault-core.ts` (Web Crypto, no Node built-ins) behind the new `VaultStore` interface, with `FileVaultStore` and `MemoryVaultStore`; `SecretVault` is now a `Vault` that keeps its constructor and additionally accepts `store`. `EvidenceStore` is now an interface (with `MemoryEvidenceStore`); the folder-based implementation is `FileEvidenceStore`, so `new EvidenceStore(dir)` becomes `new FileEvidenceStore(dir)`. `KeySource.key()` returns `Promise<Uint8Array>`. No change in behaviour or in the stored vault format; tests prove both directions against `node:crypto`. See [ARCHITECTURE.md](docs/ARCHITECTURE.md#storage-seams-in-core).
- **Demo with team sync:** `pnpm demo --team` (or `SECRET_DESK_DEMO_TEAM=1`) starts the demo with team sync set up (simulated repository `acme/team-config`, read and push, pull-request strategy, `examples/demo/secret-desk.team.config.yaml`). *Sync now* shows a small difference, *Add new entries* takes it over, *Create pull request* answers with a made-up pull request URL. The demo works on a temporary copy of `examples/demo`. New screenshots `docs/images/team.png` (after *Sync now*) and `docs/images/team-push.png` (push plan).
- **Combined status filter:** `/entries?status=soon,due` lists entries that are *Expiring soon* or *Due*; the *Due soon* tile on the Overview links to it and now counts both.

- **Anthropic: Team or Personal.** The connect dialog asks how to connect: *Team organization* (Admin key, as before) or *Personal (individual)* (a normal API key, 30 days, created by the recipe `anthropic-api-key` and checked with `GET /v1/models`). New generic facade `variants` (request field `variant`, validated server-side; `FacadeInfo.variants`); the sign-in stays shared. ### Changed

- **`@secret-desk/automation` is an optional peer of `@secret-desk/runtime`:** the runtime package no longer lists it under `dependencies` (optional `peerDependencies`, plus `devDependencies` for its own build and tests), so a project that only uses `@secret-desk/runtime/portable` installs without it. The desk app and the CLI name it in their own manifests, so what they install is unchanged. Anyone who installs the runtime package for the root entry (`createRuntime`, `createLocalRuntime`) and relied on the automation package arriving transitively now has to depend on it themselves (without it the compiler reports a plain "cannot find module" error for the root entry). The declarations of the portable entry no longer import from the automation package: the few types they named (sign-in needs and answers, the browser driver, provider and recipe) are structural stand-ins in the portable modules, and the Node modules keep using the originals. The driver in the portable declarations has every member of the original (a screenshot is `Uint8Array` instead of `Buffer`), so a host is held to the whole driver contract; a host that returns a Playwright-based driver still satisfies it. The members of `AutomationPort` that take or return these types are now properties of a function type (strict parameter comparison); `AutomationManager.run` and `attach` take the portable provider shape, which is all they read.
- **A review the queue cannot keep is no longer held without a record (`@secret-desk/runtime`):** `IssuanceQueue.add` puts the record into the store first and takes the value only after that (if anything after the `put` throws, the record is removed and the error rethrown), so a store whose `put` throws leaves no value held. `requestIssuance` and the issue branch of `resolveApproval` hand a value that was already issued at the provider to the revoke gate through the path the sweep takes for an expired review (new `IssuanceQueue.discardUnkept`), report a refusal or a failed delete as the sweep does, and rethrow the store's error; `submitManualValue` drops its value and rethrows. Behaviour with a store that does not throw is unchanged.
- **Approvals use the runtime's clock (`@secret-desk/runtime`):** `ApprovalQueue` takes an optional clock (`new ApprovalQueue(now)`, default the system clock) for `createdAt` and `decidedAt`, and the runtime builder passes its injected `now`, so every time in a runtime comes from one clock. Without an injected clock nothing changes.
- **Facade registry takes `RuntimeCore` (`@secret-desk/runtime`):** `FacadeDescriptor.verifyKey` and `FacadeVariant.verifyKey` are typed on `RuntimeCore` instead of the Node `Runtime` (they only read `fetch`); a call that passed a `Runtime` still compiles.
- **Doc comments on `IssuanceQueue.add` and `markWriteStarted`:** both are marked internal (who may call them and why); no change in behaviour or visibility.

- **Breaking for embedders (`@secret-desk/runtime`, instance state):** the `Runtime` interface gained three members that `createRuntime` always sets (`now`, `instance`, `sweep`); code that builds a `Runtime` by hand must provide them. `PendingStore` works on `PendingRecord`s, not on `PendingIssuance` objects. `commitIssuance` takes an optional `signal` in its options. `DEFAULT_NAMING` is frozen. `IssuanceQueue` takes an options object (`{ store?, now? }`) and its `get`, `list` and `claim` now treat an expired review as absent and make its value unreachable through the queue on that access (they used to return it until a sweep ran); `list()` no longer includes expired reviews. A read leaves the provider-side delete of the new value owed for the next sweep, as before: the sweep (`IssuanceQueue.sweep`, `Runtime.sweep`) also settles what an earlier read retired. `getIssuance`, `confirmIssuance` and `rejectIssuance` throw `IssuanceGoneError` (a `PolicyError`, same message) for a review that is not there. ### Fixed

- **An environment export or a rotation that fails no longer deletes a token whose identifier is in use (`@secret-desk/core`, `@secret-desk/runtime`):** three call sites asked a provider to delete a value on their own, outside the revoke gate. (1) A failed environment export (a later template entry failing, "file exists", a path outside the allowed folders, a failing write; `revokeIssuedTokens`, also called by `exportEnv`) deleted the values it had issued. A provider that rotates in place (Cloudflare Access service tokens) hands back the identifier the entry already has, and its delete removes the token object, so a failed export deleted the token that the inventory and every place still use. (2) The old-value revoke of `rotateSecret` had no "identifier unchanged" guard, so after a rotation in place it deleted the object that now holds the new value. (3) When every place failed, `rotateSecret` deleted the new value although a write that reported failure (a time-out) may have been applied by the remote. Now both flows go through `revokeNewValue`, which refuses an identifier that is the current one of the entry or of another entry the flow involves (every other secret an export issued) and refuses once a write was started. For the environment export a write is started from the moment `writeEnvFile` is about to create the file (new option `onWriteStart`), not before; for `rotateSecret` it is a place write that was sent, so after a failed rotation of all places the new token stays valid unless `rotateSecret` is called with the new option `acknowledgeWritten` (it then revokes, as before). **Behaviour change:** `exportEnv` now runs every check that needs no value (`checkEnvTarget`: path, allowed folders, not a folder, no existing file without `overwrite`, folders above are folders) before the first `issue`, because for a provider that rotates in place the issue itself replaces the value; `writeEnvFile` repeats them. An export that still fails before the file is written deletes a newly issued token with a new identifier, but not one whose identifier is the current one of any secret entry (the gate now compares against all of them, as strings), and a refusal is no longer silent: the error carries one line per kind naming the entry and the identifier. For an in-place token (the issued identifier equals the entry's current one) the line says that the provider replaced the value when it issued, the new value was lost with the failed export, every place still holds the old value, which no longer works, nothing is to be revoked (also for a provider without `revoke`), and the secret must be rotated again; the other kinds are: delete by hand, in use by another entry (do not delete), the file write had begun (the token stays valid). The result of a failed rotation carries a warning and `orphanExternalId`; after a failed or partial rotation in place the warning names the places that now hold a value that no longer works and says to rotate again (it no longer suggests writing the places again, the value is not returned); `RotateDeps.evidence` takes a report with the identifier of a new token that stays valid. A rotation whose places all failed no longer sets `newTokenRevoked` without `acknowledgeWritten`. The two old-value revokes (`issuance.ts`, `rotate.ts`) skip the delete, with a warning, when the old identifier is the new one or is still the current identifier of another entry (companions copy identifiers); the issuance flow had the first guard already and gets the second. `revokeIssuedTokens` now takes `RevokeGateDeps` and an option `writeStarted` and returns one outcome per value (`IssuedTokenOutcome`) instead of a list of names; `unrevokedNotices` and `addUnrevokedNotices` turn them into the sentences; `IssuedToken` gets the provider of the entry; `EnvBuildResult.issuedTokens` carries it; `revokeNewValue` accepts `RevokeGateDeps` (inventory, providers, connections, fetch, provider configuration) and no longer needs a GitHub client. A failed export forgets the values it put into the run (`runValues`, `forgetRunValues`) when no file was written, so a later `ref` entry cannot pick up a deleted value. The error text of a failed export has its sentences on separate lines now (it was one line). `revoke-gate-guard.test.ts` also catches `.revoke!(`, `["revoke"](`, `.revoke.call(`/`apply`/`bind` and an aliased or destructured `revoke`, and scans the providers, automation, CLI and MCP packages; one listed exception remains outside the gate in the providers (an Anthropic wrapper passing revoke on). `forgetRunValues` matches the template id exactly. `acknowledgeWritten` of `rotateSecret` must only be passed on a person's explicit action. **Not covered:** for a provider that rotates in place the `issue` call itself is the point of no return and nothing can restore the old value (the text says to rotate again); two keys of one template issuing the same in-place secret; `rotateSecret` not writing companion values; a provider whose `issue` throws after the provider side already changed; two processes changing the inventory between the issue and the revoke; the gate sees only the inventory; the old-value guards compare identifier strings over all secret entries without the provider; `rotateSecret` has no caller in the desk app, the CLI or the MCP server. Tests: `revoke-gate-rest.test.ts` (core), `export-revoke-gate.test.ts` (runtime). See [ARCHITECTURE.md](docs/ARCHITECTURE.md#instance-state-and-deadlines) and [SECURITY-MODEL.md](docs/SECURITY-MODEL.md).
- **Team export no longer carries who confirmed a value:** `exportTeamBundle` removed only `externalId` and `rotatedAt`, so `verifiedAt` and `verifiedBy` (the name of the person who confirmed) travelled in the team file and in a team-sync push. The export now removes all four local fields, driven by the same list (`KEEP_LOCAL`) that a replace import uses to keep the local values, and the push check (`assertTeamFileClean`) refuses all four. ### Security

- **Team sync hardening:** pushes require a private team repository and push permission (`team_repo_not_private`, `team_repo_no_push`; no override), and the connection test shows a *Repository is private* row. Repository owner and name, file path and branch names are validated against path traversal in the configuration schema and again in the GitHub client. The GitHub App installation token and private key are handled per operation (no process-wide cache), and the team file is rejected if it contains the own token, the GitHub token, the installation token, the App private key, a `gh*_`/`github_pat_` token shape or a PEM private key header. The headless startup (`SECRET_DESK_TEAM_REPO`) applies new entries only; changed or removed entries stay pending for confirmation. The team state file is written atomically with mode 0600, a created `inventory.yaml` has mode 0600, and a team file over 1 MiB is rejected before parsing.

## [0.1.0] - 2026-10-28

Initial release.

### Added

- **Inventory and status:** metadata-only inventory (`inventory.yaml`) of secrets, variables, stages, dev templates and custom providers; expiry status (ok, soon, due, expired, missing, no date) with configurable thresholds; offline `secret-desk check` and a workflow template that raises expiry issues.
- **Two-stage issuance with review evidence:** the provider API creates a value, the portal verifies it (function test, permissions, expiry, reachable targets), builds a review report with an evidence image and optional screenshot attachment, and writes to GitHub only after a human ticks the checklist. The old value is revoked after the write; rejecting deletes the new value at the provider again. Manual paste for providers without an API.
- **Providers:** random values (hex, base64, UUID), Cloudflare tokens and Turnstile secrets, Supabase API keys, Stripe webhook secrets (sandbox and live connections kept apart), Resend API keys, Grafana service-account tokens, and guides for GitHub fine-grained tokens, Supabase access tokens, Stripe restricted keys, OpenAI and Telegram bots.
- **Freely configurable stages:** stage `kind` (`dev`, `test`, `live`, `shared`) drives behavior; GitHub environment derived from the stage; Settings page; stages travel in the team file.
- **Variables:** `vars.*` with expected values, drift status against GitHub, apply and adopt, quick row actions, and a guard against putting secrets into variables.
- **Compare:** matrix of secrets and variables against stages and repositories with live read-only checks, parity, orphans, all repositories of the organization, what workflows need (`secrets.*`, `vars.*`), level differences, optional references, ignored repositories and detection of renamed repositories with an inventory rename.
- **Repositories and local links:** repository selection, local folder links stored outside the inventory, local search, default `.env` paths from links.
- **Integrations:** per-provider permission guides, a prefilled GitHub token link, a read-only **Test connection**, an opt-in **write test** for GitHub, and expiry tracking of access tokens.
- **Encrypted vault** for integration tokens (AES-256-GCM) with the key in the OS keychain (macOS Keychain, Linux `secret-tool`, Windows DPAPI) or a key file.
- **Browser automation:** YAML recipes driving a visible system Chrome through Playwright for providers without an API (`github-fine-grained-token`, `supabase-access-token`, `stripe-restricted-key` scaffold); `browser doctor` and `browser run --dry`.
- **Dev `.env` export** from per-repository templates (defaults, random values, personal dev tokens, variables, prompts), mode 600, never stored.
- **Team file** export and import without values.
- **Agents:** MCP server with 24 tools, a skill, and an HTTP agent API with an approval flow for everything outside `policy.agentStages`.
- **Portal:** Overview, Secrets, Variables, Compare, Repositories, Reviews, Approvals, Dev environment, Integrations, Team and Settings; German and English UI; searchable select fields.
- **CLI:** `doctor`, `check`, `status`, `renew`, `vars`, `env export`, `team`, `browser`, `vapid`.
- **Platforms:** macOS, Linux and Windows hardening (path rules, file permissions, platform-specific key sources) with simulated-platform tests and a manual cross-platform workflow.
- **Documentation:** README, guides, reference pages, OpenAPI description of the agent API, demo data, and a screenshot generator (`pnpm docs:screenshots`).

### Security

- Values are held in memory only (at most 15 minutes) and passed on only to the provider API and, sealed, to GitHub; reports, logs, errors and responses carry only a fingerprint.
- Launch secret for the portal session, `127.0.0.1` binding, Host, Origin and `Sec-Fetch-Site` checks, CSRF token, `HttpOnly` and `SameSite=Strict` cookie, Content-Security-Policy.
- Agent boundary: strict input schemas, approvals bound to the content that was requested, agent actions limited to `policy.agentStages` (never `live`), no confirmation, value entry, connection changes or attachment uploads by agents, atomic approval handling.
- Hardening: protection against `.env` injection, an allow-list for Grafana base URLs, protected bundled recipes, no key material in process arguments, vault data-loss protection, GitHub redirects followed only within GitHub, CI actions pinned to commit SHAs.
- GitHub token guidance corrected to require *Environments: Read and write*.
