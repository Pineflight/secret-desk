## [Unreleased]

### Added

- **One card per provider on Integrations:** the page and the *Add integration* picker no longer list technical connections side by side (*GitHub*, *github-app-key*, *Stripe (Sandbox)*, *Stripe (Live)*, *Stripe*, *RevenueCat Secret Key (v2)*, ...). Each provider (GitHub, Stripe, Cloudflare, Supabase, Resend, RevenueCat, Grafana Cloud, OpenAI, VesselAPI, Peecho, Telegram) is one card, grouped by category (Code and CI, Hosting and edge, Database and backend, Payments and subscriptions, E-mail and messaging, Observability, AI, Data APIs, Print and fulfilment, Other). Under a card the ways in: *Sign-in (browser)*, *API keys* (created and renewed by the sign-in for Stripe and RevenueCat, paste stays as *I already have a key*) and *By hand* (only what no API and no recipe can produce). `github-app-key` and `cloudflare-turnstile` sit under their providers as optional keys; the legacy Stripe connections `stripe`, `stripe-test` and `stripe-live` stay readable as *older connection* with a hint to replace them, nothing is deleted. Per card: status (*Connected*, *Sign-in active*, *Not set up*), keys with expiry, and the secrets and variables that depend on it (secrets of a browser recipe count for their provider). The picker is a wide dialog with a full-width search (name, category, purpose) and a keyboard and screen reader friendly tile grid. The vendor catalog (which connection, provider and recipe belong to which card, and the category) lives in one place, `packages/core/src/vendors.ts`; new routes and fields: `GET vendors`, `vendor` and `role` on `GET connections`, `vendor` on `GET providers` and on entries. Logos come from `simple-icons` (CC0-1.0, listed in THIRD-PARTY-NOTICES), bundled by `node scripts/brand-icons.mjs` (nothing is fetched at runtime), with a neutral monogram where no icon exists and a neutral color where the brand color has too little contrast. Values are created and stored exactly as before. See [docs/INTEGRATIONS.md](docs/INTEGRATIONS.md#one-card-per-provider).
- **Stripe per account and mode:** one Stripe organization holds several accounts (one per product), each with a sandbox and a live mode. Connections can now be bound to `(account, mode)`: the id is `stripe:<acct_id>:<mode>` (`sandbox` or `live`), the display label is the account name read when the connection is tested (*Stripe Acme Studio (Sandbox)*, stored next to the key as `<id>#label`). The fixed `stripe`, `stripe-test` and `stripe-live` keep working. `stripe-webhook-secret` gets the optional parameter `account` (`acct_...`): the entry then uses the connection of that account in the mode of the stage (`live` -> `live`, `test` and `dev` -> `sandbox`; `shared` needs `connection`), and `GET /v1/account` with that key must return the very account, in the preflight, before the endpoint is created and in verify; otherwise nothing is created. The connection test checks the key prefix against the mode and the account against the id. The discovery kind `stripe.account` lists the connected accounts for the parameter picker. Connection routes now accept the percent-encoded colon ids. See [docs/PROVIDERS.md](docs/PROVIDERS.md#stripe-one-connection-per-account-and-mode).
- **Recipe `stripe-restricted-key` rewritten:** creates a restricted key for one account and mode through the Stripe dashboard wizard (parameters `account`, `mode`, `preset` = `webhooks` or `full-except-sensitive`), reads the key from the attribute `data-text` of the result view (the page prints it truncated) and expires it again through the key list (*Expire key*). The sandbox wizard, the result view and the expiry were checked live on 2026-11-03 with a throwaway key; the full run, the sign-in form and the live mode (which may ask for the password; the recipe pauses for the human) are not verified.
- **Recipe engine:** `when: { var, equals }` on every step (one recipe, several modes), `click` with `optional: true` and `timeoutSeconds` (skipped when the element does not show up; used to reject a cookie banner, never to accept it), `capture.token.attribute` (read an attribute instead of the text), `exact` for `label` selectors, and `HumanWait.kind` (`login` or `pause`) so a run can tell a missing sign-in from a step that waits for the human.
- **Connect Stripe with sign-in:** the provider facade also covers Stripe. *Integrations*, Stripe, *Connect with sign-in* asks for the account id and the mode besides email and password, creates the restricted key (*Webhook Endpoints, Event Destinations: Write*), checks with `GET /v1/account` that it belongs to that account **before** storing it (a key of another account is never stored; the portal names the key to expire), stores it as `stripe:<acct_id>:<mode>` and tests it. A password confirmation asked by the live dashboard shows as "waiting for you in the browser window" instead of failing.

- **OpenAI API keys by recipe:** `openai-api-key` creates a key on platform.openai.com (owner, expiry, permission level as params), reads it from the one-time view and revokes the old one.
- **VesselAPI keys by recipe:** `vesselapi-api-key` creates a key in the VesselAPI dashboard (30, 60 or 90 days on the free plan), reads it from the one-time view and deletes the old key through the confirmation dialog.
- **Supabase database password:** the new automatic provider `supabase-db-password` sets `SUPABASE_DB_PASSWORD` through `PATCH /v1/projects/<ref>/database/password` with a locally generated password (CSPRNG, letters and digits only, `length` 24 to 64, default 40). The old password stops working immediately and there is nothing to revoke; the API gives no read-back, so the test checks shape and the 2xx answer, not a Postgres login. The preflight warns when the project is not `ACTIVE_HEALTHY`. The `supabase` connection guide lists *Database config: Write* (`database_config_write`), needed only for this provider, and normalize now suggests switching `SUPABASE_DB_PASSWORD` from `manual` to it (missing parameter `projectRef`). Not verified live. See [docs/PROVIDERS.md](docs/PROVIDERS.md).
- **Supabase scoped access tokens by recipe:** `supabase-access-token` creates a token for one organization and project with a permission preset and expiry (the form Supabase introduced in place of full-account tokens), reads it from the one-time dialog and revokes the old one. Role selectors take `exact: true` so a project name like `wake-miles` does not also match `wake-miles-staging`.
- **Provider facade with a guided sign-in (RevenueCat first):** on *Integrations*, a provider with a facade offers *Connect with sign-in*. You type the provider email and password (used for that run only), the portal signs in through the remote browser and shows every step live (opening the page, email, password, one-time code, approval in the app, CAPTCHA hand-over, signed in) with elapsed time and time limit. It then creates the integration key itself (RevenueCat: a v2 secret key, *Project configuration: Read only*, named `secret-desk-integration-<date>-<time>`), stores it as the connection (vault, else this session), runs *Test connection* and reports e.g. "1 project, 3 apps". *Check sign-in* tells whether the browser session is still valid without credentials. The dialog for such providers starts with the sign-in; pasting a key is a collapsed fallback and the token lifetime is not asked for (RevenueCat keys do not expire). Recipes get an optional `login.form` (selectors for the sign-in steps, `mfa`, `approval`, `captcha`, `failure`); `{{login.username}}` and `{{login.password}}` exist only inside `fill` values there. Routes `facades`, `facades/:id/state|sign-in|code|connect|cancel|check` are human-only (agents get 404, the MCP server has no tool). Credentials live in memory for one run, are typed only on the recipe's hosts (a redirect to a foreign host aborts), are wiped afterwards and appear in no state, log, error, screenshot or response; nothing is retried automatically. RevenueCat verification: only the email step of the sign-in page was checked live; password, code, approval, CAPTCHA and error steps are not verified. See [docs/INTEGRATIONS.md](docs/INTEGRATIONS.md#guided-sign-in-provider-facade) and [docs/SECURITY-MODEL.md](docs/SECURITY-MODEL.md#guided-sign-in).

- **RevenueCat as a source of variables:** the new connection `revenuecat` (a v2 secret key with *Project configuration: Read only*, test connection `GET /v2/projects`) reads projects, apps and the public SDK keys (production and sandbox, newest key wins) so `REVENUECAT_PROJECT_ID`, the app ids and `REVENUECAT_*SDK_KEY` are loaded instead of typed. Sources `revenuecat.project`, `revenuecat.app`, `revenuecat.publicApiKey`; the normalize suggestions know these names; the secret-shape guard accepts the public SDK key prefixes and blocks `sk_` keys. Secret keys are never a source. See [docs/INTEGRATIONS.md](docs/INTEGRATIONS.md) and [docs/RESOURCES.md](docs/RESOURCES.md).
- **Recipe parameters and a RevenueCat recipe:** browser recipes can declare per-entry `params` (key, label, optional `pattern`, `options`, `default`, `help`, `required`) that become `{{key}}` variables and provider parameter specs (so the parameter card and `params_invalid` work). A missing or invalid value aborts before the browser opens and names the key. `ParamSpec` gets an optional `pattern`. Conditions get `hidden` (waits until an element is gone), and `capture` and `mask` selectors can use variables. The new recipe `revenuecat-secret-api-key` creates a V2 secret API key with one access level per section and can revoke it (form and list checked against the live page on 2026-11-02; full run not verified). `browser run --dry` takes `--param key=value`. See [docs/RECIPES.md](docs/RECIPES.md#parameters).
- **Providers and roadmap:** [docs/ROADMAP.md](docs/ROADMAP.md) lists supported, in-progress and planned providers with their live verification status and every external service secret-desk talks to. The browser sidecar image ships its own [third-party notices](docker/browser/THIRD-PARTY-NOTICES.md) under `/licenses`.
- **Open the remote browser from the portal:** `automation.viewerUrl` (or `SECRET_DESK_BROWSER_VIEWER_URL`) adds an *Open browser* link to *Connections*, and the section text explains the server browser instead of a local Chrome window.

- **Full sync guide:** [docs/FULL-SYNC.md](docs/FULL-SYNC.md) walks through setting up many repositories in one pass: needs from the workflows, normalize, sources and parameters, GitHub environments, dry run, writing variables and secrets with the CLI (also inside the Docker container), removing old names, and the provider limits met in practice (paused Supabase projects, Cloudflare read permissions and single-zone tokens, Turnstile rotation).
- **Normalize the inventory:** a naming convention for secrets and variables (`UPPER_SNAKE_CASE`, no stage, provider spelled out, no framework prefix, canonical Supabase names, English words; `naming.renames` and `naming.keep` in the configuration) and a **Normalize** action on *Secrets and variables* that previews the changes (rename, stage, switch to a provider, variable sources, collisions, entries that stay manual) and applies the selected or all unambiguous ones. Also `secret-desk inventory normalize` and `GET normalization` / `POST normalization/apply`. Inventory only: nothing is written to GitHub. Entry ids stay. See [docs/NAMING.md](docs/NAMING.md).

- **Browser on the Pi (remote browser):** `automation.cdpEndpoint` (or `SECRET_DESK_BROWSER_CDP`) lets browser recipes run in a browser you reach over the Chrome DevTools Protocol instead of a local Chrome. The new image `ghcr.io/pineflight/secret-desk-browser` (`docker/browser`, `linux/amd64` and `linux/arm64`, built by the release workflow) runs a headed Chromium with Xvfb, x11vnc and noVNC, with the profile in a volume, a mandatory VNC password and DevTools reachable only inside the compose network. You sign in once per provider in the noVNC window; later runs need nobody watching, and a re-authentication pauses the run until you complete it in the same window. Each run uses its own tab and only disconnects at the end. `secret-desk browser doctor` (`--cdp`) and the *Connections* page report the mode and whether the endpoint answers. See [docs/DOCKER.md](docs/DOCKER.md#browser-on-the-pi) and [docs/BROWSER-AUTOMATION.md](docs/BROWSER-AUTOMATION.md#remote-browser-headless-host).

### Security

- **Team sync hardening:** pushes require a private team repository and push permission (`team_repo_not_private`, `team_repo_no_push`; no override), and the connection test shows a *Repository is private* row. Repository owner and name, file path and branch names are validated against path traversal in the configuration schema and again in the GitHub client. The GitHub App installation token and private key are handled per operation (no process-wide cache), and the team file is rejected if it contains the own token, the GitHub token, the installation token, the App private key, a `gh*_`/`github_pat_` token shape or a PEM private key header. The headless startup (`SECRET_DESK_TEAM_REPO`) applies new entries only; changed or removed entries stay pending for confirmation. The team state file is written atomically with mode 0600, a created `inventory.yaml` has mode 0600, and a team file over 1 MiB is rejected before parsing.

### Changed

- **Release workflow: the browser sidecar only when it changed.** `secret-desk-browser` is built and published only if `docker/browser` changed since the previous release tag (or no sidecar image exists yet); otherwise its `:latest` is not touched, so Watchtower no longer restarts the browser on every merge and cuts off a human sign-in. The portal image is unchanged. See [docs/DOCKER.md](docs/DOCKER.md#automatic-updates-with-watchtower).
- **Secrets and variables in one list:** the pages `/secrets` and `/variables` are now one page, `/entries` ("Secrets and variables"), with one table, a *Kind* column and a *Kind: All | Secrets | Variables* switch (`?kind=secret|variable`). The existing filters apply to both kinds; filters that exist for one kind only (provider, parameters, expiry or comparison states) are marked and never applied silently to the other. The header shows the counts ("117 secrets, 93 variables"), and one **New** action asks for the kind. `/secrets` and `/variables` redirect permanently with the query string kept; `/secrets/:id` is unchanged. Navigation, command palette, Compare, Overview and Repositories link to the new page with filters set. See [docs/ENTRIES.md](docs/ENTRIES.md).
- **Spacing system:** one scale (4/8/12/16/24/32 px) as CSS variables in `globals.css` with role tokens (section gap 32 px, 24 px below 640 px; head to card 12 px; card padding 16 px; list cells 8 x 12 px). Cards, list cells, chips and the Integrations section use them, so Secrets, Variables, Compare, Repositories, Team, Integrations and Overview share the same rhythm. Table rows and chips are more compact. Compare: the gap between repository groups was always 0 (`first:mt-0` on the head matched every group) and is now 32 px; the repository head sits 12 px above its table, has a rule and stays sticky under the top bar while scrolling.
- **English naming:** the portal routes are now `/settings`, `/approvals`, `/reviews`, `/reviews/:id`, `/variables`, `/connections` and `/compare`; the new-entry query parameter is `new=1`. All test names are English, and `assets/logo-protokoll.json` became `assets/logo-log.json` with English keys.
- **Migration:** the old German routes (`/einstellungen`, `/freigaben`, `/pruefen`, `/variablen`, `/verbindungen`, `/vergleich`) redirect permanently with the query string kept, and `?neu=1` is still accepted. Inventory, config and team files already used English keys, so nothing needs to be migrated there; bookmarks keep working through the redirects.

### Fixed

- Browser recipes name a new token with the secret id shortened and date plus time kept (at most 40 characters). Before, a long id cut the date off, so the next renewal produced a token with the same name and the old one could not be told apart for revocation.
- Secrets created by a recipe behind a facade (RevenueCat) count for that integration on the overview instead of showing 0 secrets.
- Browser sidecar: a small window manager (Openbox) gives Chromium the keyboard focus. Without it, typing in the noVNC window could stop working after the container restarted.
- The version in the sidebar and on *About* is the GitHub release tag of the running image (for example `v0.1.0-29`) and links to that release, instead of the package version `v0.1.0` that never changes between releases.
- Guided sign-in: a browser that is already signed in is recognised even when the provider redirects from its sign-in page only after a few seconds. The run then skips the form instead of failing on the missing email field.
- The *Open browser* link can be a path on the portal host (`/browser/vnc.html?...`), so it works under every address of the portal instead of one fixed host name.
- An external recipe folder that does not exist or holds no recipes is no longer reported as skipped.
- Secrets and variables list: the actions column no longer detaches from the table. The table fits its card at 1440, 1024, 768, 375 and 320 px instead of scrolling: below 1280 px kind, stage, value and targets fold into the name cell, below 640 px status and actions do too. Secret and variable rows now share one actions cell with one icon group of the same width, vertically centered (secrets: edit and open, variables: compare, set, adopt, edit, remove). Long descriptions wrap to two lines instead of widening the table.
- Lists: the actions column of the variables table is no longer cut off. Cells are narrower and the actions stay at the right edge (sticky) when a narrow window still has to scroll horizontally. Checked on the real pages at 1280, 1440 and 1920 px (no horizontal scroll in Variables, Secrets, Compare, Repositories) and 768 px (usable, actions visible).

- Integrations: connecting GitHub (and `team-sync`, `github-app-key`) no longer fails with "Unknown connection" when browser automation is off. Connections the portal offers itself return empty resources and defaults instead of an error; really unknown names still fail. Clearing the defaults of a connection that has none no longer throws.

- Container starts without internet access: `CMD` runs `next start` directly instead of `pnpm` (corepack no longer downloads pnpm at start).
- The launch address is printed when the server starts (`instrumentation.ts`), not at the first API call.
- Release workflow: image references in the manifest job are lowercased (`Pineflight/...` made `imagetools create` fail); annotations are set on the index only and the step also works with none.
- Cloudflare permission groups with the same name for different scopes (for example account and zone) are listed once, with their scopes combined, instead of twice.
- Grafana integration link: `https://grafana.com/profile/org` instead of `https://grafana.com/orgs` (404 without an org slug); with a known stack address the card links to `<baseUrl>/org/serviceaccounts`.

## [0.1.0] - 2026-10-28

Initial release.

### Added

- **Inventory and status:** metadata-only inventory (`inventory.yaml`) of secrets, variables, stages, dev templates and custom providers; expiry status (ok, soon, due, expired, missing, no date) with configurable thresholds; offline `secret-desk check` and a workflow template that raises expiry issues.
- **Two-stage issuance with review evidence:** the provider API creates a value, the portal verifies it (function test, permissions, expiry, reachable targets), builds a review report with an evidence image and optional screenshot attachment, and writes to GitHub only after a human ticks the checklist. The old value is revoked after the write; rejecting deletes the new value at the provider again. Manual paste for providers without an API.
- **Providers:** random values (hex, base64, UUID), Cloudflare tokens and Turnstile secrets, Supabase API keys, Stripe webhook secrets (sandbox and live connections kept apart), Resend API keys, Grafana service-account tokens, and guides for GitHub fine-grained tokens, Supabase access tokens, Stripe restricted keys, OpenAI and Telegram bots.
- **Freely configurable stages:** stage `kind` (`dev`, `test`, `live`, `shared`) drives behavior; GitHub environment derived from the stage; Settings page; stages travel in the team file.
- **Variables:** `vars.*` with expected values, drift status against GitHub, apply and adopt, quick row actions, and a guard against putting secrets into variables.
- **Compare:** matrix of secrets and variables against stages and repositories with live read-only checks, parity, orphans, all repositories of the organization, what workflows need (`secrets.*`, `vars.*`), level differences, optional references, ignored repositories and detection of renamed repositories with an inventory rename.
- **Repositories and local links:** repository selection, local folder links stored outside the inventory, local search, default `.env` paths from links.
- **Integrations:** per-provider permission guides, a prefilled GitHub token link, a read-only **Test connection**, an opt-in **write test** for GitHub, and expiry tracking of access tokens.
- **Encrypted vault** for integration tokens (AES-256-GCM) with the key in the OS keychain (macOS Keychain, Linux `secret-tool`, Windows DPAPI) or a key file.
- **Browser automation:** YAML recipes driving a visible system Chrome through Playwright for providers without an API (`github-fine-grained-token`, `supabase-access-token`, `stripe-restricted-key` scaffold); `browser doctor` and `browser run --dry`.
- **Dev `.env` export** from per-repository templates (defaults, random values, personal dev tokens, variables, prompts), mode 600, never stored.
- **Team file** export and import without values.
- **Agents:** MCP server with 24 tools, a skill, and an HTTP agent API with an approval flow for everything outside `policy.agentStages`.
- **Portal:** Overview, Secrets, Variables, Compare, Repositories, Reviews, Approvals, Dev environment, Integrations, Team and Settings; German and English UI; searchable select fields.
- **CLI:** `doctor`, `check`, `status`, `renew`, `vars`, `env export`, `team`, `browser`, `vapid`.
- **Platforms:** macOS, Linux and Windows hardening (path rules, file permissions, platform-specific key sources) with simulated-platform tests and a manual cross-platform workflow.
- **Documentation:** README, guides, reference pages, OpenAPI description of the agent API, demo data, and a screenshot generator (`pnpm docs:screenshots`).

### Security

- Values are held in memory only (at most 15 minutes) and passed on only to the provider API and, sealed, to GitHub; reports, logs, errors and responses carry only a fingerprint.
- Launch secret for the portal session, `127.0.0.1` binding, Host, Origin and `Sec-Fetch-Site` checks, CSRF token, `HttpOnly` and `SameSite=Strict` cookie, Content-Security-Policy.
- Agent boundary: strict input schemas, approvals bound to the content that was requested, agent actions limited to `policy.agentStages` (never `live`), no confirmation, value entry, connection changes or attachment uploads by agents, atomic approval handling.
