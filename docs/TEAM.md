# Team

## Distributing the configuration file
`secret-desk team export --config secret-desk.config.yaml --out secret-desk.team.yaml` (or in the portal: Team, Download).
The file contains the structure: expiry `thresholds`, stage definitions (`stages:`), secrets (name, stage, provider, parameters, targets, expiry data), variables with expected values, dev templates and
custom providers. **No values**, and no provider-internal identifiers (`externalId`) or `rotatedAt`. Variable values are configuration, not secrets. Open the file before you share it: descriptions and links are part of it.

## New team member
1. Clone the repo, `pnpm install`, `pnpm build`.
2. `secret-desk team import secret-desk.team.yaml --inventory inventory.yaml`.
3. Create your own configuration (GitHub access, provider connections).
4. Dev environment per repo: `secret-desk env export --config secret-desk.config.yaml --repo <repo>`.
   It contains defaults and variables from the inventory, random values and **personal** dev tokens that your account creates at the provider.
   Values you have to supply yourself (for example a sandbox key) are asked for (`--prompt KEY=VALUE`).

The `.env` is created on your machine with mode 600. The portal does not store it.

## Team sync with a private GitHub repository
Instead of passing the team file around by hand, a team can keep it in a private GitHub repository (any `owner/name`, path and branch) and let the portal sync with it. Configure `teamSync` ([Configuration](CONFIGURATION.md#teamsync)) or use the first-start wizard. The file is the same team file as above: structure only, no values.

### Choose the repository from lists
Nothing is typed. On the welcome page (empty inventory) *Load the team configuration from a GitHub repo* shows lists that are read from GitHub with the GitHub integration (the same token resolution as above; discovery uses the connection `github` or the GitHub App):

1. **Repository.** A searchable list of the repositories the integration can see (owner and name, private or public, last push). It is preselected when the name contains `team-config` or `secret-desk` (the most recently pushed first). If no name matches, the portal looks for `secret-desk.team.yaml` in the few most recently pushed private repositories (at most five requests) and preselects one that has it. **Public repositories are listed but cannot be chosen**, with the reason: team sync needs a private repository.
2. **Branch.** All branches; the default branch is preselected.
3. **File.** The matching files on that branch (`secret-desk.team.yaml`, `*.team.yaml`, `secret-desk/*.yaml`), read with one tree request. The conventional name is preselected. If nothing matches, the list offers *New file secret-desk.team.yaml*: the file is created with the current configuration by the **first push** (*Team*, *Push to repo*), so this needs *read and write*. The portal says so; nothing is written during setup.
4. **Mode.** *Read only* or *read and write*, each with the rights it needs shown next to it (*Contents: Read*; *Contents: Read and write*, plus *Pull requests: Read and write* for the pull-request strategy). Each mode is checked against the integration with the same checks as the *Team repository* connection test (repository readable, private, team file, rights granted to a GitHub App installation, push permission). A mode the integration cannot do is marked with what is missing. For *read and write* you also choose pull request or direct commit.

Then *Load preview* saves the setting and shows the preview as before; nothing is taken over until you confirm.

**No token field.** If GitHub is not connected, or the connection lacks a right, the page names what is missing (and the rights needed) and links to *Integrations* instead of asking for a token. A token you type yourself stays available only under *Use a different token* (collapsed): it is kept for this session and used instead of the integration.

**Routes.** The lists come from `GET /api/ui/team-sync/discovery/repos`, `.../branches?repo=`, `.../files?repo=&branch=` and `.../access?repo=&branch=&path=&mode=&strategy=`. They only read, answer without any token and are **human routes only**: agents get 404, because listing the repositories of the integration is a human decision. GitHub's rate limit is respected (one retry after `Retry-After`, otherwise the page asks you to wait); lists are capped (1000 repositories, 500 branches). *Team* shows the saved setting; changing it later is done by setting `teamSync` again through this page or the configuration file, the *Team* page has no typed fields of its own.

**Roles.** Everyone reads. In `mode: pull-push` the people who may change the team structure also push. The repository decides who may merge: with `push.strategy: pull-request` (the default) a push only opens or updates a pull request, and your normal review and branch protection apply.

**Token.** By default team sync **uses the GitHub integration**; no extra token is needed. Resolution order: an own `team-sync` token (session, vault, `connections.team-sync`, `SECRET_DESK_TEAM_TOKEN`) wins, otherwise the connection `github`.
- *GitHub token (PAT):* used as it is, so its repository selection and rights apply: the team repository must be selected, with *Contents: Read* (sync) or *Read and write* (push) and, for pull requests, *Pull requests: Read and write*.
- *GitHub App* (`github.auth.type: app`): for every operation (one check, take-over or push) the portal reads the App private key and requests a short-lived installation token (nothing is cached across operations) for **this one repository** with exactly `contents` (read, or write to push), `pull_requests` (write, only for the pull-request strategy) and `metadata: read`. No hand-made token. The App must have these permissions (App settings, Permissions: Contents and Pull requests) and its installation must include the team repository (Repository access); the installation owner is the owner of `teamSync.repo`. Note that these are rights beyond the ones for secrets and variables. **Push also requires that GitHub reports `permissions.push` for the repository** (`GET /repos/{owner}/{repo}`) in the answer to the installation token: if the field is absent, the portal cannot establish the right and fails closed (*team_repo_no_push*) instead of trusting the granted installation rights alone; both must say yes.
- *Own token:* the *Team token* below, or one you create yourself. It is needed only when the GitHub integration cannot reach the repository or you do not want to widen it. GitHub cannot create fine-grained tokens through the API; the *Team repository* card under Integrations links to the GitHub form with name, owner, expiry and the exact rights prefilled and says which repository to select. Where browser automation is available you can create an inventory entry with the provider `github-fine-grained-token` instead (not in the container).

**Team token (created for you).** Instead of widening the general GitHub integration token, the portal can create a **separate team token** for exactly this job. On the setup page (below the mode cards) and on *Team* there is the button *Create team token*. It opens GitHub in the browser (browser automation, not available in the container without the browser sidecar), uses the recipe `github-fine-grained-token` and creates a fine-grained token that is
- limited to **this one repository** (*Only select repositories*) and the owner you picked,
- valid for **90 days**, named `secret-desk-team-<repo>` plus date and time (shortened to 40 characters when needed),
- given exactly the rights of the chosen mode and nothing else: *read only* (`pull`) = Contents: Read, Metadata: Read; *read and push* (`pull-push`) = Contents: Read and write, Pull requests: Read and write, Metadata: Read (with `push.strategy: direct` the pull request right is left out).

You never leave the portal. When the remote browser is signed out of GitHub, the run asks in the portal for the sign-in way (email and password, *Continue with Google*, *Continue with Apple*), types it on GitHub's own pages for this run only (memory, wiped afterwards, never logged or stored), and asks for the authenticator or SMS code, the number to tap in GitHub Mobile or the first-use authorization right there. When GitHub asks *Confirm access* (sudo mode) the portal asks how you confirm: **GitHub Mobile** (default: the portal shows *Open GitHub Mobile and tap 17*), an **authenticator code**, or your **password** (typed once, masked in screenshots). A passkey cannot work in the remote browser and is not offered. If GitHub Mobile is not approved in time, or a code or password is refused, the portal says so and asks again (up to three tries). The steps show as a timeline (opening, signing in, confirming access, creating, testing, deleting the old token, ready). *Check sign-in* tells you whether the remote browser is signed in at GitHub before you start. The viewer of the remote browser is a developer tool only; the selectors of the sign-in and of *Confirm access* are partly not verified live (see [BROWSER-AUTOMATION.md](BROWSER-AUTOMATION.md#confirming-access-confirmaccess)).

The new token is **tested with itself before it counts**: it must read the repository (which must be private) and the branch and, for read and push, report push permission. Only then it is stored as the connection `team-sync` (vault if enabled, otherwise this session), with its expiry; the repository, mode and token name are kept next to it (entry `team-sync#meta`, never the value). If the test fails nothing is stored and the previous state stays; the page names the token at GitHub so you can delete it. After success the mode shows *Ready · team token, valid until <date>*.

Why a separate token: the integration token (or App) can stay as narrow as it is for everything else; team sync gets one token that can touch one repository. Team sync **prefers it** over the integration, but only where it fits: a token made for `acme-org/team-config` with read rights is not used for another repository or for push mode (the integration answers there), and lists of repositories on the setup page always use the integration.

**Renewal and old tokens.** The token expires after 90 days (then the integration is used again until you create a new one; the page says so). Changing the repository or mode later offers *Create a new team token*. After the new one works, the portal **deletes the replaced token at GitHub** with the `revoke` section of the recipe (Settings, Developer settings, Fine-grained tokens, the row by name, *Delete*, confirm; *Confirm access* is asked in the portal like above) and the timeline shows *Deleting the replaced token at GitHub*. This `revoke` section is not verified live. Only when that run fails, the old token is shown as *Delete the old team token at GitHub* with its name, **the reason the delete run failed** and a link to [GitHub's fine-grained tokens page](https://github.com/settings/personal-access-tokens): delete it there yourself and press *I deleted it*. A failed delete never undoes the new token. A token you type in by hand for `team-sync` also retires the portal's token the same way.

**Routes (human only).** `GET /api/ui/team-sync/token` (state: availability, active token, pending deletion, current run), `POST team-sync/token` (`{ repo, mode, strategy?, branch? }` starts the run), `POST team-sync/token/cancel`, `POST team-sync/token/check` (sign-in check), `POST team-sync/token/revocation-done`, and the answers to the questions of a running run: `POST team-sync/token/credentials` (`{ method, username, password }`), `/code` (`{ code }`), `/confirm` (`{ accept }`) and `/access` (`{ method: mobile | code | password, code?, password? }`). The run state carries `ask` (the question to answer) and never a typed value. They need the portal session and CSRF header like every portal route; agents get 404 and there is no MCP tool. No response carries the token.

The portal checks instead of guessing: the connection test of *Team repository* (and `GET /api/ui/team-sync/status`, `neededRights`, `tokenSource`) reads the repository and the file, tries to list pull requests when the pull-request strategy needs them and, for a GitHub App, compares the rights GitHub actually granted with the needed ones. *Write test* (`POST connections/team-sync/check` with `deep: true`) creates a probe branch and deletes it again to prove Contents write. A missing right is shown as a finding with the exact rights and how to extend them (token: repository access and rights; App: rights and installation). Token values are never shown.

**Pull.** When the portal starts (`pullOnStart`) and on *Sync now* (Team page, or `secret-desk team pull`) the portal reads the file read-only and compares it with the local state. It tells you whether everything is equal, the repository is new or changed, only you changed something, or both sides changed. Before anything is taken over you see a preview: which secrets, variables, stages, providers and dev templates would be added, changed or are only local (names and ids, no values). Taking over uses the merge logic of `team import` (new entries are added, existing ones stay); *replace* needs an explicit confirmation. The blob SHA of the last synced file is kept locally in `.secret-desk-team-sync.json` next to the configuration file to recognize changes on both sides.

**Conflicts.** If the repository and the local inventory both changed, nothing is overwritten silently. You see the difference and choose: take over the repository (merge or replace), keep local (the repository state is marked as seen, a later push will overwrite it), or cancel.

**Push.** In `mode: pull-push` the Team page shows *Push to repo* (or `secret-desk team push`). The portal exports the team file, checks that it contains no values, `externalId` or `rotatedAt` (and neither the access token, nor the token of any connected provider, nor anything shaped like a Stripe, RevenueCat, Supabase, OpenAI, Anthropic, Cloudflare, Resend or GitHub key or a PEM private key), shows the difference to the repository and asks for one confirmation for all pending changes. Then it commits one file: with `pull-request` to `push.branch` and opens (or updates) a pull request against `branch`, with `direct` straight to `branch`. Pushes are rate-limited (at least 30 seconds apart) so clicking repeatedly does not create a commit each time. Errors (no network, expired token, 403, 404, conflict) are reported and nothing partial is written. Portal changes are not pushed automatically: they show up as *local changes*, and you push when you are ready.

**Agents.** AI agents may read the status (`GET /api/agent/team-sync/status`). Checking, taking over and pushing are human actions in the portal or the CLI.

**CLI.** `secret-desk team status|pull|push --config secret-desk.config.yaml`. `pull` shows the preview; `--apply merge|replace|keep-local` takes over (`--confirm-replace` for replace). `push` shows the difference; `--yes` confirms.

## Resource mapping in a team
The `resourceMap` (repository to provider resource, see [RESOURCES.md](RESOURCES.md#mapping-repositories-to-resources)) is exported with the rest and contains only ids and display names, no secrets. On import (merge), an entry whose key (`kind`, `repo`, `stage`) already exists locally stays unchanged and new keys are added; `--replace` takes over the list from the file (and removes the local list if the file has none). Resource ids belong to a provider account: a teammate who connects a different account sees *The mapping points to a resource the provider does not know* until the mapping is adjusted.

## Stages in a team
Stage definitions are exported along with the rest (see [STAGES.md](STAGES.md)). On import (merge), unknown stage ids are added and existing ones stay unchanged (no silent change of kind or
environment); `--replace` takes over the list from the file completely and keeps the local fields `externalId`, `rotatedAt`, `verifiedAt` and `verifiedBy` of secrets with the same id. In the portal, *Replace* needs an explicit confirmation (`confirmReplace`).
