# Architecture

## The path of a new value

```text
Provider API ──> value in memory ──> verification ──> review report + evidence image
                                                          │
                 human ticks the review items (attachment optional)
                                                          ▼
                 write to GitHub (encrypted) ──> re-check ──> revoke old value ──> inventory + report
```

1. **Prepare** (`prepareIssuance`): the provider module creates the value (or a human pastes it in). The portal checks length,
   that the targets are reachable with write permission, and provider-specific findings (active, permissions, expiry, mode). The result is a
   **review report** (metadata only) and an **evidence image** (SVG). The value stays in memory for **at most 15 minutes**.
   Nothing is written to GitHub and the old value is not revoked.
2. **Confirm** (`commitIssuance`): all review items must be ticked; a failed automatic finding blocks the step (unless `force` is used).
   Then: write to all targets, re-check (name exists, just changed), revoke the old value at the provider, record `rotatedAt`, `expires`,
   `verifiedAt` and `verifiedBy` in the inventory, and store the report with the confirmation. If a target fails, the old value stays valid and
   the review stays open.
   **Companion values:** a provider may return values for other inventory entries from the same answer (`IssuedSecret.companions`, for
   example the client ID next to the client secret). Only entries the provider names in its params (`companionParams`) can receive one, in
   the same stage; this is checked before anything is issued. The report lists them (name, targets, fingerprint), confirm writes them in
   the same commit and records `rotatedAt` and `externalId` on them, and reject, expiry or a changed target discard them with the main value.
   When the provider renews in place (new id equals old id), nothing is deleted on confirm or discard.
3. **Discard** (`discardIssuance`): on rejection or timeout the new value is deleted at the provider again. Nothing was written.

## Data

- **Inventory** (`inventory.yaml`, in Git): secrets (name, stage, provider, expiry, targets), variables (including the expected value),
  dev templates, custom providers. Metadata and configuration only, never a secret value.
- **Who writes the inventory:** the portal, the CLI, the MCP server and scripts, all through `InventoryStore` (`packages/core/src/inventory.ts`) on the same file. The store follows the file: it reloads when the content hash differs (stat pre-check on every read, `fs.watch` on the directory in the portal as a hint, `onExternalChange` listeners to drop derived state: open approvals whose entry changed become `stale`, the cached team-sync comparison is cleared), and the file's version counter (`GET inventory/version`) lets open pages reload silently. Every change is applied as a function of the document and remembered until it is saved. `save()` takes a lock file, compares the file with the content the change was based on and, if it differs, loads the fresh content, replays the changes and writes it (temp file, `fsync`, `rename`, mode `0600`). A change that no longer fits, a full replacement (`replaceData`, the team import) over a changed file, or a file that is invalid on disk ends in `InventoryConflictError` (409) and writes nothing. See [CONFIGURATION.md](CONFIGURATION.md#inventory-inventoryyaml).
- **Review reports and attachments** (`.secret-desk-evidence/`, not in Git): reports as JSON, screenshots as PNG/JPEG/WebP up to 5 MB.
- **Memory:** issued but not yet confirmed values, the session's access tokens, pending approvals.
- **Local files** in `~/.secret-desk/`: the encrypted vault for integration tokens (`vault.json`), folder links (`repo-links.json`), the agent token and the browser profile. See [CONFIGURATION.md](CONFIGURATION.md#files-secret-desk-writes).

## Platforms
Path, permission and key questions live in `packages/core/src/platform.ts` (`securePrivateFile`, `ensurePrivateDir`, `writePrivateFile`,
`expandHome`, `isPathInside`, `realpathLoose`, `localPathProblem`, `sanitizeFileName`) and in the `KeySource`s of `vault.ts` (macOS Keychain,
Linux `secret-tool`, Windows DPAPI via PowerShell, optional key file). Everything takes `platform` (and, for commands, an `exec` function)
as a parameter, so Windows and Linux behavior can be tested on any system with `path.win32`/`path.posix` and a fake exec.
Only these commands are started: `git` (runtime/core), `op` (core), `security`/`secret-tool`/`powershell.exe` (core, vault), Chrome (Playwright).
Scripts in the repo are Node files under `scripts/` (`clean.mjs`, `demo.mjs`, `screenshots.mjs`), not shell lines.

## Repositories and links

- The **Repositories** page (`/repos`) combines the inventory (secrets, variables, templates), GitHub live (`GET repos?live=1`, names and metadata only)
  and local links. Without a GitHub connection it quietly falls back to the inventory and links.
- A **link** maps a repository to a folder on this machine. It is stored in `~/.secret-desk/repo-links.json`
  (mode 600, folder 700; config field `linksFile`), never in the shared inventory. The server checks the path, `.git` and the remote
  (`git remote get-url origin`; a mismatch is only a warning).
- **Scan locally** searches `policy.envRoots` down to depth 2 for Git folders whose origin points to the configured owner and
  proposes links. Nothing is applied until you click.
- For a linked repository, the Dev environment page and `env-export` use `<folder>/<template file>` as the default path. An explicit path wins.
- Endpoints (portal only): `PUT repos/:name/link`, `DELETE repos/:name/link`, `POST repos/scan`. Agents may only call `GET repos` (without paths).
- The repository fields in forms are select fields (inventory, GitHub, linked); free input remains possible.

## Stages

Stages are freely configurable: the `stages:` section in the inventory (portal: Settings). See [STAGES.md](STAGES.md). A definition has `id` (slug), `label` (display name), `kind`,
`environment` (name of the GitHub environment) and `tone` (color). Without `stages:`, `dev`, `staging`, `production` and `shared` apply.

Behavior depends on the `kind`, never on the name:

| kind | Meaning |
|---|---|
| `dev` | local: no GitHub target needed, agents may act directly (per `policy.agentStages`, default all dev stages), Dev `.env` |
| `test` | sandbox/test: provider keys are expected to be in test mode |
| `live` | production grade: agents always need an approval, keys must be in live mode, warning styling |
| `shared` | applies to all (for example a repository secret), mode is not checked |

If `environment` is missing: for `test`/`live` it is the `id`, for `dev`/`shared` there is none. `null` means explicitly none. For scope `environment` without a name,
secret-desk fills in the stage's environment (a name is only stored when it differs). Staging and production never share a value. At most 12 stages;
a stage can only be removed when no secret, variable, template or policy refers to it. The `organization` scope is in the schema but not in the portal form:
organization secrets need a repository selection that is not modeled yet.

## Stage comparison

The **Compare** page (`/compare`), `GET compare` and the MCP tool `desk_compare_stages` show which secrets and variables exist on which stage and where something is missing. It is read-only and never returns a value. The pure logic is `compareMatrix` in `packages/core/src/compare.ts` (inventory plus optionally pre-read GitHub names, testable without network); the network part is `compareStages` in `packages/runtime/src/compare.ts`; workflow parsing is `packages/core/src/workflow-needs.ts`. Cell states, parity, orphans, workflow needs, ignored and renamed repositories are described in [COMPARE.md](COMPARE.md).

## Storage seams in core

Three interfaces separate what `packages/core` does from where the bytes live, so the core can run in a runtime without a file system:

- **Vault:** `Vault` (`vault-core.ts`) encrypts with AES-256-GCM through Web Crypto and talks to a `VaultStore` (`read`, `write`) and a `KeySource`. `FileVaultStore` (`vault-file-store.ts`) is the JSON file of the local edition, `MemoryVaultStore` the in-memory one. `SecretVault` (`vault.ts`) is a `Vault` with the file store and the operating system key sources as defaults; its constructor also accepts `store`. The stored format did not change: an entry written before the split is read by `Vault` and the other way round (tests: `vault-core.test.ts`).
- **Evidence:** `EvidenceStore` (`evidence.ts`) is the interface for reports and attachments, `MemoryEvidenceStore` the in-memory implementation, `FileEvidenceStore` (`evidence-file-store.ts`) the folder-based one. One contract test runs the same cases against both.
- **Inventory:** the store keeps its synchronous getters and all of its logic: refresh gating, adopting or rebasing an external change, the retry loop of `save()`, problem handling, versioning and listeners. That logic is `InventoryStoreCore` in `inventory-store.ts`, which imports no Node built-ins; `InventoryStore` in `inventory.ts` is a thin Node facade that extends it with `open(path)` and builds the file backend, so every existing import keeps working. Only the I/O primitives sit behind an `InventoryBackend` (`inventory-backend.ts`): `stamp()` (a cheap change stamp compared by string equality), `read()` (text plus an opaque revision), `withWriteLock(fn)` (the only writer; hands `fn` a transaction with `read()` and `write(text, expected)`, which writes only if the stored revision still equals `expected` and otherwise reports `written: false` so the store can rebase and retry) and an optional `watch(hint)`. `FileInventoryBackend` (`inventory-file-backend.ts`) is the file of the local edition: stat-based stamp, sha256 revision, lock file next to the file, temp file plus fsync plus rename. `InventoryStore.open(path)` and `fromText(text, path)` build it; `InventoryStore.withBackend(backend, initial?)` takes any other backend. The error classes live in `inventory-errors.ts` and are re-exported by `inventory.ts`. `MemoryInventoryBackend` (in `inventory-backend.ts`) is the in-memory implementation: one document, a counter as revision, writers queued one at a time, and `replaceExternally(text)` to simulate another writer (it calls the `watch` hints). `inventory-contract.test.ts` runs the same behaviour cases against the file and the memory backend.

What a backend must guarantee: `read()` and `stamp()` never throw and agree (a changed text has a changed revision; an unchanged revision under a new stamp is harmless); `withWriteLock` runs one writer at a time and rejects with an explanatory error if it cannot; `write(text, expected)` checks the stored revision against `expected` (`null` = nothing stored yet) and reports `written: false` on a mismatch instead of overwriting. A hosted backend has exactly one writer per document and stores the text in one row with a version: the version is the revision and the compare-and-set on it is the expected-revision check. Concurrent edits from other sessions then show up as `written: false`, and the store rebases its unsaved changes on the new text and retries; it never writes over a newer version.

`vault-core.ts`, `evidence.ts`, `inventory-backend.ts`, `inventory-errors.ts` and `inventory-store.ts` import no Node built-ins and do not use `process`, `Buffer` or `require`; `portable-modules.test.ts` fails if that changes. Everything that needs the file system or the operating system stays in `vault.ts`, `vault-file-store.ts`, `evidence-file-store.ts`, `inventory-file-backend.ts` and `platform.ts`.

### Portable entry point

`@secret-desk/core/portable` (`packages/core/src/portable.ts`) re-exports only the modules that import no Node built-ins and no libsodium: `secret`, `stages`, `types`, `inventory-store`, `inventory-errors`, `inventory-backend`, `evidence`, `vault-core`, `connections-core`, `variable-sources` and `github-core` (the GitHub client, see below). A runtime without Node APIs (for example a Cloudflare Worker) imports from there and does not pull in `node:fs`, `node:child_process` or libsodium. The Node facades (`SecretVault`, `InventoryStore`, `ConnectionStore`, the file stores, `platform`, the Node facade of the GitHub client) stay on the package root; the root keeps all its exports. `packages/core/package.json` also sets `"sideEffects": false`, so a bundler can drop the unused Node modules when only portable names are imported from the root.

The rule: a module is added to `portable.ts` only if it is portable, and then it is added to the guard. `portable-modules.test.ts` takes `portable.ts` as a root, follows its relative value imports, expects exactly the known set of files, fails on Node built-ins, `process`, `Buffer`, `require` and on any npm import other than the allowlisted pure packages (`yaml`, `zod`), and checks that `portable.ts` exports every runtime name of those modules.

### Running the store contracts on another implementation

The contract suites for the three storage seams are importable from `@secret-desk/core/testing` (`packages/core/src/testing/`): `inventoryBackendContract`, `vaultStoreContract` and `evidenceStoreContract`. The repository runs them against the memory and file implementations (`inventory-contract.test.ts`, `vault-store-contract.test.ts`, `evidence-contract.test.ts`); an implementation elsewhere (for example on a SQL database in a runtime without Node built-ins) runs the same suites against its own store instead of restating the contracts. The subpath is not re-exported from the package root or from `./portable`, so application bundles never contain test code.

Each suite takes the test framework as its first argument, `{ describe, it, expect }` (Vitest or anything Jest-compatible), so the package imports no framework and has no peer dependency; the same code runs under Node and inside a Workers test pool. The factory builds a fresh store per test and may be async. It returns the store plus an optional `cleanup`, which runs after the test, also when it failed.

```ts
import { describe, expect, it } from "vitest";
import { evidenceStoreContract, inventoryBackendContract, vaultStoreContract } from "@secret-desk/core/testing";

const framework = { describe, it, expect };
vaultStoreContract(framework, "SqlVaultStore", async () => ({ store: new SqlVaultStore(await freshDatabase()), cleanup: dropDatabase }));
evidenceStoreContract(framework, "SqlEvidenceStore", async () => ({ store: new SqlEvidenceStore(await freshDatabase()) }));
inventoryBackendContract(framework, "SqlInventoryBackend", async (initial) => {
  const db = await freshDatabase(initial); // `initial`: the text already stored, null = nothing stored yet
  return { backend: new SqlInventoryBackend(db), writeExternally: (text) => db.replaceRow(text), stored: () => db.readRow() };
});
```

The inventory harness needs two things the backend interface does not offer: `writeExternally(text)` (another writer replaces the stored text; the revision and the stamp must change) and `stored()` (the text stored right now, `null` = nothing). The suite moves the clock itself by replacing `Date.now` for the length of one test, which is what the store reads, so no fake-timer library is needed.

A store that can only be used inside a special context passes `{ run }` as the last argument: `run(body)` wraps the body of every test (the factory is called inside `body`), so the runner can enter that context (for example an isolated object) and call `body` there. Every test builds its own store through the factory; nothing is shared between tests through module state. The suites are covered by the repository's own tests and guarded by `portable-modules.test.ts` as a separate root (no Node built-ins, no `Buffer`, no test-framework import).

### Host capabilities

`ConnectionStoreCore` (`connections-core.ts`, portable, covered by `portable-modules.test.ts`) holds the token lookup: session value, vault, then the configured source. What the hosting process lets a configuration reach is an explicit `ConnectionHost` (`label`, optional `env(name)` and `readReference(ref)`). Without `env`, an `env` source is not available; without `readReference`, an `op` source is not available. Both cases throw a `NotConnectedError` that tells the user to enter a token under Connections, and `status()` reports the same reason without throwing. Session and vault values are looked up first and work either way. `ConnectionStore` (`connections.ts`) is the Node facade of the local edition: it keeps the options `env` and `exec`, builds `nodeConnectionHost(env, exec)` (process environment and `op read <ref>`) from them, and accepts `host` to override it; `host: null` means no host at all. Omitting `host` on `ConnectionStore` grants the process environment and `op`: that default is for the local edition only. A runtime that shares one process between several users uses `ConnectionStoreCore` or `host: null` so a configuration cannot read the host's environment or run its tools.

`nodeConnectionHost` answers `env(name)` only for an own property of the environment object whose value is a string (a source named `toString`, `constructor` or `__proto__` is "not set", not an inherited function), and refuses a reference that does not start with `op://` before a process is started; the reference is passed to `op read` after `--`.

#### Host capability of the runtime

`createRuntime` (`packages/runtime/src/runtime.ts`) takes an optional `RuntimeOptions.host` of type `RuntimeHost` (`packages/runtime/src/host.ts`). `RuntimeHost` extends `ConnectionHost` (`env(name)` reads one environment variable by name, `readReference(ref)` reads one 1Password reference) with `runCommand(command, cwd)` (one allow-listed template command), `gitOrigin(dir)`, `gitCheckIgnored(path)`, `homeDir()` (the home folder), `openVault(options)` (the default vault with its OS key source), `launchLocalBrowser(options)`, `connectRemoteBrowser(options)` and `findChrome(preferred)`. Every member is optional and an absent member means "not available". The host is passed in code by the embedder; configuration and requests can neither add a member nor widen one, and the members take values (a name, a command key, a folder), never a command line. `runEnvCommand` additionally refuses any command name that is not in its allow-list.

Without a host (option omitted or `null`) the runtime code in `packages/runtime/src` does not read the process environment or the home folder of the process and does not start a process; the only exception is that the YAML parser we depend on looks at its own debug switches `LOG_TOKENS` and `LOG_STREAM` while it parses (the behavioural test excludes exactly these two names). There is no fallback to the Node host. The paths that used to reach the machine on their own:

| Path | Without a host | With `nodeRuntimeHost()` |
|---|---|---|
| `env` and `op` connection sources (`ConnectionStore`) | `NotConnectedError` / status "not available in this environment" | process environment, `op read -- <ref>` |
| Team token from `SECRET_DESK_TEAM_TOKEN` (`runtime.ts`) | no `team-sync` connection is added | `host.env` |
| Team start-up settings `SECRET_DESK_TEAM_REPO`, `_PATH`, `_BRANCH` (`startupTeamSync`, `teamSyncFromEnv`) | not read; the headless setup is skipped | `host.env` |
| Remote browser address and viewer address (`AutomationManager`, `viewerUrlFrom`) | variables not read; only `automation.cdpEndpoint` and `automation.viewerUrl` of the configuration apply | `host.env` |
| Default vault (`runtime.ts`; the file store and the OS key source read the environment and start the OS key tools) | no default vault: an embedder passes `vault` itself; the vault is shown as off | `host.openVault` (with `~` paths expanded by `host.homeDir`) |
| Local browser (`AutomationManager`: the driver, the Chrome lookup behind `info()`) | no driver and no Chrome lookup: `BrowserNotAvailableError` (kind `browser-unavailable`), `info()` reports "not available" | `host.launchLocalBrowser`, `host.findChrome` |
| Remote browser at a configured `automation.cdpEndpoint` (an outbound connection, no process) | also refused (the address comes from configuration), `BrowserNotAvailableError`, no reachability probe; the public option `automationDriver` (`driverFactory`) replaces the browser and is not affected: with it a browser is available whatever the host offers and the status probe of a configured address still runs | `host.connectRemoteBrowser` |
| Home folder (`repos.ts`, `settings.ts`, `automation.ts`, `runtime.ts`: `~` paths, default links file, default browser profile, allowed link root) | the home of the process is neither an allowed link root nor a default location; a `~` path is refused with `HostCapabilityError` (`InventoryError` for a link request) and a default location needs an explicit path (`linksFile`, `automation.profileDir`); `persistSignIn` needs `linksFile` | `host.homeDir` |
| Template commands (`exportEnv` with `runCommands`) | not run; the entries stay empty, `skipped` lists them and a warning says why | `host.runCommand` (`supabase status`), and only in a folder under `policy.envRoots` or the linked folder of the repository (real path checked before anything starts; empty and relative `envRoots` entries are ignored); the repository's own `node_modules/.bin` binary is used only when it really lies inside that folder. That binary is code controlled by the repository: a `node_modules/.bin/supabase` inside an allowed root or linked folder runs when a person with `runCommands` asks for the template command there |
| Git ignore check of a written env file (`writeEnvFile`) | not run; `gitIgnored` is `null` | `host.gitCheckIgnored` (`git -c core.fsmonitor=false -c core.untrackedCache=false check-ignore -q -- <path>`) |
| Git remote of a linked folder (`repos.ts`: `setLink`, `scanLocal`, `listRepos`) | not run; no remote is known, `setLink` warns that it cannot be checked, `scanLocal` finds nothing | `host.gitOrigin` (`git -c core.fsmonitor=false -c core.untrackedCache=false -C <dir> remote get-url -- origin`). Both Git calls get an environment built from the host's own environment source (system basics, no provider tokens) with `GIT_CONFIG_NOSYSTEM=1` and `GIT_CONFIG_GLOBAL` set to the null device, so neither the system nor the user's Git configuration applies; a repository's own `.git/config` still does, which is why the two `-c` switches turn off the settings that would run a program (on git 2.54 a plain `git check-ignore` runs a configured `core.fsmonitor` program, the switched call does not) |

The single-user local edition passes the Node host explicitly: `createLocalRuntime(path, options)` is `createRuntime` with `nodeRuntimeHost({ env, exec })` (the portal, the CLI and the tests use it). `createLocalRuntime` is also what the portal's demo mode uses, with `vault: null` so the demo never opens the real vault. Two tests guard the boundary. `host-capability.test.ts` is the proof: it builds a runtime without a host from a configuration with the defaults (vault and automation on), replaces the process environment with a recording proxy, makes the child-process starters throw and puts fake `git`, `op` and `supabase` programs on `PATH`, then reads a connection token, builds an environment file with `runCommands`, links a repository, runs a recipe and calls `info()`; nothing may be read or started. `host-guard.test.ts` is the tripwire: it fails when a file under `packages/runtime/src` other than `host.ts` reads the environment, imports `node:os`, `node:module` or `node:child_process`, uses `process[...]`, `getBuiltinModule`, `Bun` or `Deno`, or uses `new SecretVault`, `defaultKeySource`, `PlaywrightDriver` or `findChrome`; `portable-modules.test.ts` does the same for the portable part of the core.

The path checks (the real path of the command folder, the allowed link roots, `writeEnvFile`'s roots) are check-then-use: they assume the allowed roots and the linked folders are not writable by an attacker while a request runs. Importing the runtime does not use the home folder through the runtime's own code; the Node modules of the core and the automation package still compute `DEFAULT_VAULT_FILE` and `DEFAULT_PROFILE_DIR` with `os.homedir()` once at import (the OS lookup, not the process environment object; both constants are public and used by the CLI, so they stay), and nothing in the runtime uses their values without a host.

Still outside the capability: file access through configured paths (the runtime reads and writes its configuration, inventory, evidence, links and state files at the paths the configuration names, and writes env files under `policy.envRoots`; a hosted environment must give each tenant its own configuration or backends); `loadConfig` and the other Node modules of `@secret-desk/core` (`vault.ts`, `env-export.ts`), which are Node facades and not covered by the guard; `probeCdp` in `@secret-desk/automation` (an outbound request, reached only when the host allows a remote browser or a test passes a driver factory); and the browser processes started by `@secret-desk/automation` only through `launchLocalBrowser`.

### Injectable cryptography

Two cryptographic operations of the GitHub client can be supplied by the host, so the client also runs where the default implementations are not available or not wanted:

- **Sealing a value** for the GitHub secret store: `GitHubClientOptions.seal` takes a `SecretSealer` (`(publicKeyBase64, plaintext) => Promise<string>`) that returns the Base64 (original variant) of an anonymous sealed box (X25519, XSalsa20-Poly1305, nonce = BLAKE2b-192 of the ephemeral and the recipient public key). Without it the client uses libsodium (`github-seal-libsodium.ts`), which `github.ts` loads lazily on first use; a client with an injected sealer never loads it. This matters in runtimes that cannot compile WebAssembly at run time.
- **Signing the GitHub App JWT:** `GitHubAppOptions.sign` takes an `AppJwtSigner` (`(signingInput) => Promise<string>`) that receives `base64url(header).base64url(payload)` and returns the base64url RS256 signature. Exactly one of `privateKey` and `sign` must be given; with `sign` the private key never enters the process of the provider.

**Portable GitHub client.** The client lives in `github-core.ts` (no Node built-ins, no `Buffer`, no libsodium, no zod; guarded by `portable-modules.test.ts`) and is exported from `@secret-desk/core/portable` as `GitHubClient` and `githubAppProvider`. It has no defaults for the two operations above: `seal` and `sign` must be passed by the caller. Without `seal`, sealing (`seal()`, `putSecret`) throws a `GitHubError` ("no sealer configured") before anything is sent; without `sign`, `githubAppProvider` throws at construction. Base64, Base64URL and UTF-8 conversions use the small helpers in `base64.ts` (`TextEncoder`, `TextDecoder`, `btoa`, `atob`, chunked for large inputs). `placeKey` and the snapshot types moved to `place-key.ts` (re-exported by `status.ts`), so the client does not import `types.ts` and the zod schemas as values. `github.ts` is the Node facade with the same exported names as before: `GitHubClient` is a subclass that defaults `seal` to the lazily loaded libsodium sealer, and its `githubAppProvider` still accepts `privateKey` (signing with `node:crypto`) or `sign`.

The local edition passes neither: it seals with libsodium and signs with the private key held in the process. Both paths produce the same bytes as before (tests: `github-injection.test.ts`). libsodium is now loaded at the first seal, so a missing or broken libsodium surfaces at the first write or write probe instead of at start-up. `GitHubClient.seal(publicKeyBase64, plaintext)` seals through the client's sealer and checks the result before anything is sent (a non-empty Base64 string that is neither the plaintext nor its Base64, otherwise a `GitHubError`); `putSecret` and the connection write probe both use it, so an injected sealer covers the probe too.

## Instance state and deadlines

A runtime can be embedded more than once in one process (several tenants), or in a process that is evicted and restarted at any time (a serverless runtime). Two rules follow, and tests hold both.

**Everything a runtime holds while it works lives in the runtime instance.** The waits for a person (the one-time code, the authorization question and the identity-verification question of the provider sign-in flows, and the four questions of the team token run), the live-check flag and the pending reviews belong to one `Runtime`: `Runtime.instance` (`InstanceState`, `instance-state.ts`) and `Runtime.issuances`. Nothing is kept in module scope, so a code typed for one runtime can never be taken by another, even when both wait on the same provider. `instance-isolation.test.ts` creates two runtimes, starts a wait in one and delivers the answer to the other (refused, not consumed, not visible) and the reverse. `state-guard.test.ts` fails when a file under `packages/runtime/src` or `packages/core/src` declares module-level mutable state: `let`/`var`, a `Map`, `Set`, `WeakMap`, `WeakSet` or any other constructed object, an array or object literal that is not frozen, or a mutable static class field (it reads each declaration as a whole: multi-line initialisers and arrow types in annotations included). Constants that are built once and only read stay, if they say so: a `readonly`/`Readonly*` type, `as const` or `Object.freeze(...)`. The scan cannot see what a called function returns; the isolation tests are the proof. Explicit, justified exceptions (listed in the test): the three object-keyed `WeakSet`s in the core's `issuance.ts` (committing, committed, discarded), which are keyed by the pending item itself and cannot carry anything from one runtime to another (an object belongs to one runtime), and two read-only byte fixtures of the importable store contract suites.

**Every access checks its deadline; no timer is needed for correctness.** `RuntimeOptions.now` is the clock (default: the system clock) and is `Runtime.now`.

- *Pending reviews* (`IssuanceQueue`, `issuances.ts`): `get`, `list` and `claim` compare `expiresAt` with the clock first. An expired item is treated as absent and removed on that access: the queue holds no reference to the value (or the companion values) any more and replaces the ones it kept, so the value is **unreachable through the queue**. Strings cannot be erased in this runtime: a caller that kept the object still has the value, and the memory is not overwritten. The one thing a read cannot do is the network call that deletes the new value at the provider: that stays owed and is done by the next sweep (`Runtime.sweep`, a new issuance). A missed sweep therefore never extends the reachability of a value; it only delays the delete at the provider.
- *A claim is bounded, with limits.* A review that an operation has claimed (confirm or reject in progress) is hidden past its deadline but held for that operation, and only until its deadline plus `CLAIM_GRACE_MS` (two minutes). From then on every access (`get`, `list`, `claim`, `sweep`) takes it back: the claim is broken, the signal of the claim (`IssuanceQueue.signal`) fires, and the item is retired like any other. The commit is cut off *between writes*: `commitIssuance` checks that signal and, with `options.hardBound` (the same bound read from the clock), the clock before every write, so a commit that comes back later writes nothing more and reports the remaining places as failed. What this does **not** do: a write that is already in flight is not cut off (the GitHub client takes no abort signal), and a commit whose single write never settles keeps its own captured reference to the value for as long as that call hangs. So "whatever the operation is doing" holds for the queue's references and for the next write, not for a call that is already out.
- *A write that was started is a fact of the item.* Before a commit sends its first write it records the fact: in memory on the item (`hasWriteStarted`) and, through the `beforeWrite` hook, in the store (`PendingRecord.writeStarted`, `IssuanceQueue.markWriteStarted`); when the store update fails the commit writes nothing. It is never cleared. A write that throws or times out counts as started, because the remote may have applied it; the places a write was started for (`writtenPlacesOf`) are named in the evidence report (`partial-write`). The commit marks the item committed as soon as every place holds the new value, so a failing evidence store afterwards is a warning in the result.
- *Waits* (`WaiterBook`): each question has a deadline of its own, **counted from the moment it is asked**: `WAIT_WINDOWS_MS` has a named window per kind (credentials 15 minutes; code, authorization and identity verification 10 minutes; none longer than `DEFAULT_WAIT_MS`). It is not taken from the start of the run, so a long sign-in cannot leave the next question expired before it is asked. `answerable`, `get` and `take` refuse a wait at or past its deadline, remove it and reject its promise with `WaitExpiredError`; both flows map that to their time-out failure code ("Time limit reached while waiting for your answer."). Every wait also carries the identity of the run that asked (its signal) and an answer is only taken for that run; a question that replaces another rejects the old one.
- *The sweep hook.* `Runtime.sweep(now?)` removes everything that has expired (reviews, with the provider-side delete of values *this process issued and still knows to be unconfirmed*, when the revoke gate allows it, and waits) and returns the earliest deadline that remains (`Date`) or `null`. An embedder calls it from a timer or from an alarm and re-arms with the result; a claimed item counts at its hard bound, an owed provider-side delete at its next try. The queue never decides with a time earlier than one it has seen. The sweep does **not** revoke records it holds no review for (see the next two points). The local edition (`apps/desk`) keeps its one-minute interval and only calls `rt.sweep()`. The sweep is deliberately not behind the authorisation hook (see "Unattended routines"): a hook must never be able to extend the life of a value.
- *The store of pending reviews* is pluggable: `RuntimeOptions.pendingStore` takes a `PendingStore` (`put`, `get`, `list`, `delete`); the default is `MemoryPendingStore`. The store is handed a `PendingRecord` only: identifier, secret id, the entry's provider at issue time, created-at, expires-at and the provider's identifier of the new value (when one would have to be deleted), plus `companionIds`, `writeStarted` (a write of the value was ever started) and `needsDecision` (the gate refused because of it). **Never the value**: the queue keeps the values itself in a map the store cannot reach, so "a store never persists the value" holds by construction, and a store may return copies. The queue does not ask the store for the answer to "is this review there": that is the value map. When the value is gone (an evicted and rebuilt process) the review flow reports `IssuanceGoneError` (a `PolicyError`, code `issuance-gone`; the portal answers 404 with that code and its review page already says that reviews expire and offers to generate the value again). It is a normal outcome, not a fault.
- ***The revoke gate: one function decides, in one place.*** The rule: revoking a value that is in use is worse than leaving an unconfirmed value valid until the provider expires it; in doubt nothing is revoked, the record is kept and the case is reported. `revokeNewValue` (`packages/core/src/issuance.ts`) is the only code that asks a provider to revoke a newly issued value. Commit's two stale checks, `discardIssuance`, the sweep (first try and retries), a person's reject and `IssuanceQueue.revokeOrphan` all go through it, and so do the two flows that issue a value outside a review: the **environment export** (a value issued for a template entry whose export then fails) and the **rotate flow** (the new value when no place took it). `revoke-gate-guard.test.ts` fails when a provider's `revoke` is called, taken as a value or destructured anywhere else in the core, the runtime, the providers, the automation package, the CLI or the MCP server, except at the listed places. It refuses, without calling the provider, with a typed reason:
  - `write-started`: a write of this item was ever started (the item's own fact, or the record's). Only an explicit acknowledgement lifts it, which only a person's reject (`acknowledgeWritten`) or `revokeOrphan(..., { acceptPartial: true })` supplies. The record is kept and marked `needsDecision`, `RuntimeOptions.onNeedsDecision` is told (a record, never a value) and an evidence note is written when the report exists; this also happens when such a review expires or goes stale.
  - `value-in-use`: the identifier equals the current external id of **any** secret entry in the inventory (compared as strings, without the provider; the entry itself, a companion and an entry nobody named alike), read at that moment (another review of the same provider identifier may have been confirmed, or a confirm left its record behind).
  - `secret-gone`, `provider-changed`: for a record alone, the entry must still exist and have the provider the record names (with the entry as it was issued, in memory, its provider and parameters are used instead).
  - `no-id`, `no-revoke`: nothing to call.
  The refusals other than `write-started` mean the record is stale and it is dropped. **Outside the gate on purpose:** the undo inside `prepareIssuance` (no item exists yet, nothing was written, the value was created a moment ago) and the two old-value revokes, which delete the value that was *replaced*, after every place holds the new one: the one after a confirmed commit (`issuance.ts`) and the one after a rotation (`rotate.ts`). Both have two guards of their own and skip the revoke, with a warning in the report or the result, when the old identifier equals the new one (a provider that rotates in place: the old value is the object that now holds the new one) or when another secret entry outside the flow still has it as its current identifier (companions copy identifiers, so such an entry can still use the value). Both guards, like the gate, compare identifier strings over all secret entries of the inventory without looking at the provider (two providers that happen to use the same string make them refuse, which leaves a value valid, never deletes one). The gate itself takes `RevokeGateDeps` (inventory, providers, connections, fetch, provider configuration): it never writes, so it needs no GitHub client.
  - **What "a write was started" means for a flow that is not a review.** *Environment export:* the file write. It counts as started from the moment `writeEnvFile` is about to create the file, after the path, the allowed folders, the existing-file check and the folder creation passed (`onWriteStart`, which `exportEnv` uses). Every check that needs no value (`checkEnvTarget`: path usable, inside the allowed folders, not a folder, no existing file without `overwrite`, the folders above are folders) runs **before the first value is issued**, so an export that is bound to fail on the target does not issue at all; `writeEnvFile` repeats the checks. A failure before the write started that remains (a later template entry failing, a command failing, a change of the file system between the check and the write) leaves the file unwritten, so the issued value may be deleted, unless its identifier is the current one of an entry. A failure after that, for example the Git ignore check, does not: the value may be in the file, the gate refuses with `write-started`. No template command receives an issued value (commands only produce values); if one ever did, receiving it would count as a write. A value handed to a later template of the same run (`runValues`) is forgotten when the export failed before the file write started, so a later `ref` entry cannot pick up a value that was deleted; after the write started it stays, because the value is still valid. *Rotate flow:* a place write that was sent. A write that threw or timed out counts, because the remote may have applied it, so when every place failed the new value is not deleted either (`write-started`), unless a person passes `acknowledgeWritten`; when only some places failed it is never deleted.
  - **What the caller reports.** Where the gate refuses, the caller says so and does not hide it: the error of a failed export carries one sentence per kind, each on its own line, with the entry and the identifier: **in place** (the issued identifier equals the entry's current one: the provider replaced the value when it issued, the new value was lost with the failed export, every place still holds the old value, which no longer works, nothing is to be revoked, rotate the secret again and write its places; with the file write started it says the new value is at most in the file; the same text for a provider that has no `revoke`), to delete by hand (the provider failed or cannot delete), in use by another entry (do not delete) and written (the file may hold the value, the token stays valid). The result of `rotateSecret` carries a warning and `orphanExternalId` (the identifier that is still valid at the provider) for a value that stays and is not in use, and the warning names the places that were not written; after a failed or partial rotation in place it says the same as the export (the value is not returned, so "write the places again" is never advice: the secret must be rotated again). A new token that stays valid after a failed rotation is also noted in an evidence report when `RotateDeps.evidence` is set (identifier and fingerprint, never the value). `acknowledgeWritten` must be passed only on a person's explicit action.

  **Known limitations:**
  - The gate knows only the inventory: an identifier that is in use outside the inventory is not seen. Inside it, every secret entry counts, named by the flow or not.
  - For a provider that rotates in place **the `issue` call itself is the point of no return**: it has replaced the old value at the provider when it returns. If the export or the rotation fails afterwards, nothing here can restore it, and the new value is gone with the failed run: the places hold a value that no longer works. The text says so; the fix is to rotate the secret again. Only the checks before the first `issue` can prevent it, which is why the export runs them first.
  - Not covered: two keys of one template that issue the same in-place secret (the second `issue` replaces the first value); `rotateSecret` does not write companion values; a provider whose `issue` throws after the provider side already changed (nothing was returned, so nothing is reported); two processes that change the inventory between the `issue` and the revoke (the gate reads the inventory at the moment of the revoke).
  - `rotateSecret` is exported from the core but nothing in the desk app, the CLI or the MCP server calls it; its behaviour is covered by tests, not by a product path. The environment export is reachable from the portal and the agent API.
  - `revoke-gate-guard.test.ts` is a text check of source files, not a proof. It sees `.revoke(`, `.revoke?.(`, `.revoke!(`, `.revoke.call(`/`apply`/`bind`, `["revoke"](`, `const f = p.revoke`, `f(p.revoke)` and `{ revoke } = p`. It does not see a call through a name it does not know (a computed key that is not a plain string, a function passed in from outside, `eval`). One call in the providers package is listed: the Anthropic provider (`withAnthropicAdmin`) delegates its revoke to the provider it wraps when no admin connection exists; it is a provider implementation passing a call on, not a flow that issues values.
  - The portal has no control to send the acknowledgement (`acknowledgeWritten` in the body of `POST reviews/:id/reject`) and does not list reviews kept for a decision. The API, `IssuanceQueue.orphans()` and the `onNeedsDecision` callback exist; the product surface is follow-up work.
  - Two reviews of one secret can be confirmed concurrently (this was already so before); the gate's `value-in-use` check reads the inventory at the moment of the revoke and cannot see a confirm that is still in flight.
  - `revokeOrphan` refuses a record that is not an orphan yet (`not-expired`: its deadline plus `CLAIM_GRACE_MS` has not passed and it is not flagged `needsDecision`), because with two runtimes on one store a record without a value here may be the other runtime's live review.
  - A revoke that a person acknowledged adds an evidence check (`revoked-written`) naming the places a write was started for; an explicit orphan revoke cannot name them (this process does not know them). When the delete fails after a person's acknowledged reject, the owed entry keeps the acknowledgement, so its retries are not refused as `write-started`. A value the provider issued without naming an identifier cannot be deleted: the gate refuses with `no-id` and the report says that the provider named no identifier.
- *States and sequences.* While a commit is in flight the sweep leaves the item alone and looks again later; a commit that ended `committed` is never revoked; a partial item (write started, not committed) is never revoked by the sweep. Re-confirming a partial item whose entry went stale revokes nothing: the item leaves the queue and stays as a flagged record for a person. A person's reject of an item a write was started for is refused with `IssuanceWrittenError` (code `write-started`, the places that were or may have been written; the portal answers 409 with that list) unless the call carries `acknowledgeWritten` (a body field of `POST reviews/:id/reject`). A reject removes the queue entry after the discard settled, and a delete the provider did not confirm is owed in a `finally`; a failed delete on the stale path is owed too. A discard's delete result is kept apart from saving its report, so a failing report store never leads to a second revoke of an already revoked identifier. When the provider returns no identifier for the new value, a successful commit clears the entry's external id instead of keeping the revoked old one.
- *Records without a review (orphans) are never revoked by a sweep.* A record whose value is gone (an evicted or dead process, a confirm whose record removal was lost, a commit that needs a person's decision, a delete the sweep gave up on) is listed by `IssuanceQueue.orphans()`; `Runtime.sweep` does not touch it. Revoking it is the explicit call `IssuanceQueue.revokeOrphan(id, deps, { acceptPartial? })`, which returns the gate's typed outcome (`revoked`, `failed`, or `refused` with the reason, plus `held-here` and `unknown`). A confirm removes its record on the success path before it returns; a persistent store should remove it in the same step as the inventory takes the new identifier, and whatever order remains, a leftover record is harmless because of the gate.
- *A failed delete is tried again, with limits.* A delete of the new value of an expired review (or of a review a person rejected, when the provider did not confirm) that fails is not reported as settled: it is tried again after a growing wait (`REVOKE_RETRY_MS` times the number of tries; the sweep skips it until then, so repeated calls cannot use the tries up), at most `MAX_REVOKE_TRIES` times in all. Any error out of the discard counts as a failed try, never as settled; only "a commit is in flight", "committed" and "discarded" are understood states, and a refusal of the gate is a decision, not a failure (it is not retried). When it gives up, the evidence report gets a note, `RuntimeOptions.onRevokeAbandoned` is told (a record, never a value), and the record stays as an orphan. A later success corrects nothing silently: it adds its own evidence note.
- *Existence is not probed with the hook.* For an id nobody knows, confirm and reject answer "gone" without asking the authorisation hook: a hook call per guessed id would write one audit entry per guess and could consume a per-action approval. Review ids are random, so they cannot be guessed; an authenticated person can tell "gone" from "not allowed". The clean-up sweep inside confirm runs after the person was authorised, never before.
- *One clock.* The runtime's own deadlines (reviews, waits, the team token run's time-out and timeline) use `RuntimeOptions.now`. The time-outs inside the browser automation package (sign-in and recipe waits) use the system clock.

## Authorisation hook

The runtime has one extension point for a process that embeds it and wants to add rules of its own, for example roles or approval by a second person, without forking: `RuntimeOptions.authorize` (kept on `Runtime.authorize`). This repository ships no such rules and stays a single-user tool; with no hook configured, nothing changes.

- **Opaque principal.** `Actor` has an optional `principalId`: an opaque, stable reference supplied by whatever authenticates the request. This repository never interprets it. The portal and the CLI build their actors as before and set none.
- **Recording.** A pending review records `preparedBy` (`ActorRef`: `name`, `kind`, optional `principalId`; who caused it to run), `requestedBy` (who asked, for example the agent) and `approvalId` when it came from an approval. An approval records `requestedBy` (name, for compatibility), `requestedByRef` (`ActorRef`), and `decidedBy` and `decidedAt` when a human approves or denies it. The confirmation in the review report gets a `principalId` next to `by` when the confirming actor has one. `verifiedBy` in the inventory stays the display name. All of this is names and ids, never a value.
- **The hook.** `Authorize = (request) => void | Promise<void>`. It receives a copy of `{ actor, action, subject? }` and refuses by throwing; returning `undefined` (or a promise of it) means allowed, any other return value (`false`, an object) is a refusal. A `PolicyError` is passed on unchanged. Anything else it throws, a return value, a hook that does not settle within `RuntimeOptions.authorizeTimeoutMs` (default 10000 ms) or a hook that is not a function becomes one generic German refusal (`Die Berechtigungspruefung hat die Aktion nicht zugelassen.`), so no hook internals or values reach a response. The optional `RuntimeOptions.onAuthorizeFault` callback is told the action, the reason and, for a throw, the class name of the error (never its message); a throwing callback changes nothing.
- **A third actor kind, `system`, for unattended work.** The request the hook receives has `actor: Actor | SystemActor`. `SystemActor` is `{ kind: "system", name }` with `name` from the closed list `SYSTEM_ROUTINES` (`team-sync-startup`, `sign-in-scheduler`, `live-check-scheduler`); it has no principal id. It is a separate type on purpose: `Actor` (what the portal, the agent API and the CLI build, and what every policy function takes) and `ActorRef` (what a review or an approval records) stay `human` or `agent`, so a `system` value can neither be recorded as `preparedBy`/`requestedBy` nor pass a policy function (`requireHuman` refuses it). Only the runtime builds a system actor, inside `authorizeSystem`, from a fixed routine name. Nothing from outside can produce one: the router takes the kind from the route prefix (`/api/ui` is `human`, `/api/agent` is `agent`) and reads no kind, actor or principal from the body, query or headers (`x-agent-name` only sets the display name and a name of `system` is still an agent); the MCP server only calls the agent API; and the actor path `authorize` refuses any actor whose kind is not `human` or `agent` (reason `invalid-actor` in `onAuthorizeFault`) without asking the hook. A hook that does not know the kind should refuse it, which is what any rule written for `human` and `agent` does by default.
- **Unattended routines ask the hook too.** `authorizeSystem(rt, routine, action, subject?)` asks the hook with the system actor and answers `true` or `false`; it never throws. The failure rules are the ones above, from the same function: any non-`undefined` result, a throw, a timeout or a hook that is not a function is a refusal, a refusal that is a fault is reported to `onAuthorizeFault` (a deliberate `PolicyError` is the hook's own decision and is not reported as a fault), and no hook internals or values reach a log or a response. The report carries `routine` (the fixed routine name) when the fault came from a routine, so an operator can tell a scheduled refusal from a person's; it is absent for a person's request. A refusal skips that unit of work, never crashes the process and never stops a timer (the scheduled routines ask again at their next turn). The start-up sync is the exception to "asks again": see its row for what a refusal leaves behind. With no hook, nothing is asked and nothing changes. See the list under "Unattended routines" below.
- **Claim on pending reviews.** Confirm and reject claim the pending item synchronously before the hook is awaited (`IssuanceQueue.claim` and `release`). A second operation on a claimed item is refused ("wird gerade bearbeitet"), the claim is released when the hook refuses or the operation fails, and after the hook the item must still be the same object. Core refuses to commit or discard an item that was already discarded, committed or is being committed, so a slow hook cannot lead to a double discard or a commit after a discard.
- **An approval is also asked for what it causes.** `approval.resolve` is followed, on approve, by `issuance.prepare` (plus `automation.run` when a browser run starts) or `variable.apply` on behalf of the approving actor, with the approval id and the requester in the subject. A refusal leaves the request pending.
- **Built-in rules always apply first.** The hook is consulted only after the built-in checks (`requireHuman`, stage policy, parameter and secret guards) have passed, and before the first side effect. It can therefore only refuse what the built-in rules allow: an agent calling a human-only action is refused by the built-in rule and the hook is not asked. A hook cannot weaken a built-in rule. For the human-only portal routes that are gated in the router (team sync, stages, repository links, browser and sign-in flows, deep connection check) the route table is the built-in rule, so agents never get that far; checks of ids and bodies inside those handlers run after the hook.
- **Actions** (`AuthorizedAction`): `issuance.prepare` (a request that prepares a review or creates an approval request; a dry run is not asked), `issuance.confirm`, `issuance.reject`, `issuance.manual-value`, `approval.resolve`, `inventory.edit` (secrets, variables, providers, templates, integration defaults, resource map, normalization), `variable.apply`, `integration.connect` and `integration.disconnect` (storing or removing a connection token in the portal), `evidence.attach`, `automation.run` (a browser run starts: a human's issuance request, a live check, a session check, the start of a team token run; also each scheduled live check and each scheduled sign-in check, for the system actor), `github.sync`, `team.sync.apply` (also the new entries taken over at start-up, subject `mode` `merge`, system actor), `team.sync.push`, `team.sync.configure` (team sync setup, dismissing the setup or a revocation notice; also the setup from the environment at start-up, system actor), `team.import` (subject `mode`: `merge` or `replace`), `settings.edit` (stage definitions), `repo.link` (repository link set, remove and rename), `connection.check` (only the deep check, which probes write access), `env.export` (content export and file export; subject `repo` and `stage`). In the guided sign-in flows of providers and recipes and in the team token flow, the steps that accept a credential, a one-time code, a confirmation or that create and store a key are `integration.connect` (subject `connectionId`: the facade, recipe or connection id).
- **Subject** (ids and actor references only, never a value): `secretId`, `variableId`, `approvalId`, `connectionId`, `repo`, `stage`, `mode`; for `issuance.confirm` and `issuance.reject` also `preparedBy`, `requestedBy` (name), `requestedByRef` and `approvalId`; for `approval.resolve` and what an approval causes also `requestedBy` and `requestedByRef`. That is what a second-person rule needs: refuse `issuance.confirm` when the actor and `subject.preparedBy` are the same party (compare kind and principal id, not display names), or refuse `approval.resolve` when the approver is `subject.requestedByRef`. A review that a human approved on behalf of an agent's request is prepared by the approving human and requested by the agent.
- **Unattended routines** (everything the process does on its own, found by reading every timer, scheduler and start-up routine of the runtime and the portal server). Asked, as `{ kind: "system", name }`:

  | Routine (name) | Where | Action and subject | A refusal |
  |---|---|---|---|
  | Start-up team sync (`team-sync-startup`) | `startupTeamSync`, the setup from the environment | `team.sync.configure` before the configuration is written, `team.sync.apply` (subject `mode: merge`) before the new entries are taken over | that step and the rest of the start-up sync are skipped. Refused at `team.sync.configure`: nothing is written (configuration file, inventory and team state are untouched) and the next start asks again. Refused at `team.sync.apply`: the configuration was already written by the allowed first step, so the inventory stays empty and the team state unchanged, but the next start no longer enters the set-up-from-environment branch and neither asks nor applies; this is not retried automatically, a person applies the sync in the portal (which asks the hook as that person) |
  | Scheduled sign-in checks (`sign-in-scheduler`) | `SignInScheduler.tick` | `automation.run` once per due host; subject `connectionId`: the recipe id | no browser is opened for that host and no sign-in answer is recorded; the time of the attempt is remembered, so the host is not asked again before the retry time (default 30 minutes) and is asked again after it, like a failed check; one log line (no value) says it was not allowed; the other hosts go on |
  | Scheduled live check (`live-check-scheduler`) | `LiveCheckScheduler.tick` | `automation.run` once per due run, no subject | nothing runs, nothing is stored or sent to the notification address, one log line says so, the tick answers `skipped: "refused"`; the check stays due and the next tick asks again. Ticks that come in while the hook is still asked do not ask or run a second time |

  The checks are asked with the same action as the manual ones (`automation.run`), the actor tells them apart. The live check logs one line when it turns from allowed to refused, not one per tick.

  Not asked, on purpose: the **expiry sweep** of unconfirmed reviews (`Runtime.sweep`, which the portal timer calls every minute and an embedder calls from its own timer or alarm, and the sweep that a new issuance and a confirm run first; the deadline checks on every access are not asked either). It is clean-up: it only discards a value held in memory and revokes the new value at the provider, and it writes no value anywhere. A hook must never be able to extend the lifetime of a value, so a refusing, hanging or faulty hook has no say here and the sweep is identical with or without a hook. Also not asked, because they only read local state or read from a remote without changing anything that matters: the inventory file watcher (`watchInventory`, re-reads the local file into memory), the read-only check of the team repository at start-up with `pullOnStart` (the check a human starts in the portal is not asked either; it only keeps the last answer in memory and, when both sides are equal, the hashes in the team state file), the display-only reads of the portal (status, listings, previews), and the continuations of a run that an actor already started and the hook already allowed (the background half of a sign-in flow, a team token run, a manual live check). The timers in the portal's browser code only refresh the display.
- **Left unhooked, on purpose.** Operations that only read (listings, plans, previews, the plain connection check, the repository scan, the push plan, `team-export`, which carries structure and never a value) and the cancel steps of browser runs (they only close a run). The command line (`secret-desk ...`) is out of scope for the unattended routines: it builds its own runtime without a hook, starts no timer, and what it runs (for example a live check) is run by the operating-system user on purpose. The commands that go through the runtime functions are asked as above when a process embeds the runtime with a hook, the commands that act on a local file as the operating-system user (for example `team import --inventory`) are not. The MCP server talks to the agent API of the portal, so it passes the same checks.
